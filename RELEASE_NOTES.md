# StarNet v0.14.2

Stations without a voice key speak again: Microsoft's free voice had been refusing StarNet since mid-October. A key you pasted into a chat is no longer sent to your AI service from other chats and background work. YOUR FIRST TASK no longer covers the message box, Gmail goes straight to app-password setup, and skills keep their files; approving one sticks. The terminal gains /connect, FLOOR and /split. StarNet's send and upload tools now take files only from an agent's workspace or project folder.

## Voice is back

- **Stations without a voice key speak again.** Since mid-October, Microsoft's free read-aloud voice, the one StarNet uses when you have no OpenRouter, Gemini or OpenAI key, has refused StarNet's requests, so those stations stayed silent when reading replies aloud unless they used StarNet's built-in voice (0.13.5 and 0.14.1 included). StarNet now connects the way that service expects, and in our checks against Microsoft's live service the voice answers again.
- **Sentences that were cut off now play in full.** Earlier versions could save half a sentence when the free voice cut it off partway, then replay it cut short every time that line came back. Clips saved before this update by the free voice or a paid voice are no longer used: each sentence is made again in full the first time it's needed and saved whole. On a paid voice, that means a line StarNet had already saved is billed once more.
- **When your agent can't speak a sentence, StarNet says why.** If every voice StarNet tries fails, the note beside the speaker button in COMMS and the button's tooltip now name the voice and the reason, for example "OpenRouter rejected the key (HTTP 401)", instead of only "voice synthesis failed" or "unreachable". A refusal that won't clear up in seconds is no longer retried on every sentence: replies stay as text for a minute, or until you turn the speaker off and on again.
- **StarNet checks the free voice when it starts.** About 15 seconds after it starts, StarNet asks Microsoft's free voice service to read one fixed test line ("StarNet voice check.") and writes whether it answered to sidecar.log, next to startup.log. It does this even if you don't use voice, and nothing you've said is sent. To turn it off, set `STARNET_EDGE_TTS_PROBE=0` and restart StarNet.

## Your keys stay out of other chats and background work

- **Keys you pasted into a chat no longer ride into other chats and background work.** Before this update, a key you had pasted into a chat could ride along when StarNet reminded an agent of earlier work (recent activity, task briefs, the night shift, learned topics), so it was sent to your AI service again on later requests. StarNet now takes keys out of what it brings back from earlier work, and a key saved in CONNECTED › API KEYS appears there by its name instead. Keys typed before the update stay in your saved history but are kept out of other chats and background work. Still sent as before: the conversation you pasted the key into, a key written into a routine's own instructions, and a password that doesn't look like a key and isn't saved in StarNet. If you pasted a key into a chat before this update and want to be safe, replace it at the service that issued it.
- **Keys StarNet keeps for you are taken out of what agents send.** When a key saved in CONNECTED › API KEYS shows up in a file, a web page or a message an agent works with, your AI service now gets its name, like [GITHUB_API_KEY saved in API KEYS], instead of the key; your AI service key and chat-app tokens become [redacted-secret]. Agents still use a saved key by its name in web requests and commands. Because the agent no longer sees the key itself, an agent that rewrites a whole file holding one can write that placeholder in its place, so check such a file after an agent edits it.
- **Keep keys in CONNECTED › API KEYS, not in a dossier.** An API key written into your COMMANDER DOSSIER, an AGENT DOSSIER, a goal or a quest is now hidden from agents, which see [redacted-key] or the saved key's name in its place. An agent that reads back a loop, a note or a skill sees its keys hidden too, and so does the full copy StarNet saves in the agent's workspace when one of those answers is too long. Because the agent sees the placeholder, an agent that rewrites a loop's objective or a skill's file from what it read back can save the placeholder in place of the key, so check them after an agent changes them. Save the key in CONNECTED › API KEYS and agents can use it by its name.
- **A message with a key in it shows once.** After you reopened a session, a message holding a key could show twice in COMMS, and StarNet's saved copy of the conversation kept the key as typed. It now shows once with the key hidden, there and in the save. The newest message still waiting for an answer keeps your exact words, so ↻ Try again resends what you typed.
- **StarNet hides keys more accurately.** In new messages in COMMS, your saved history, the `starnet` terminal and chat apps, a name like task-management-dashboard no longer shows as ta[redacted-key], and placeholders such as ${API_KEY}, $DB_PASSWORD or <your key> after password=, api_key: or Authorization: stay as written; a password typed the same way, like $SECRET2024 or <hunter2>, now shows as written too. The credential after Authorization: Basic or Token is now hidden (before, the word Basic was hidden and the credential showed), and so is a GitHub, Google, Slack or similar key, or a password= value, right after an escape code, as in JSON text, a web address or colored terminal output. In JSON text written without spaces, a web address that ends in a port and is followed by an email address, as in {"url":"http://localhost:8080","owner":"me@x.com"}, no longer loses everything from the port to the email's @. Messages saved before the update don't change.
- **Run titles leave out keys.** The title StarNet records for each new run, shown for example in HUD MODE and as a conversation's name in the `starnet` terminal, no longer keeps a key StarNet recognizes or holds for you from the message that started it. Titles saved before the update are unchanged, and the name of a session you start in COMMS can still show a key from its first message.
- **In a browser tab, speaking to StarNet sends OpenRouter only your OpenRouter key.** If you opened StarNet in a web browser tab and saved another AI service's key there (an Anthropic or OpenAI key, say), StarNet could send that key to OpenRouter when it turned what you said into text. The desktop app's own window never holds your keys, so it wasn't affected. If this applies to you and you want to be safe, replace that key at the service that issued it.

## Files leaving your station

- **Files your agents send come from the folder they work in.** In a project chat, a file an agent had just made and then sent to a chat app (Telegram, Discord, Slack, Matrix or Signal) or attached to a web request was looked for in its own workspace instead of the project folder, so it went missing or an older file with the same name was sent. A short file name now means the project folder in a project chat and the agent's own workspace elsewhere, the same rule its file tools use. A file in either folder can also be named by its full location, such as a screenshot the agent just took. When a file can't be attached, the chat note names it by its short name, not its full location on your computer. In a project chat that started before this update, a short name the agent used earlier for a file in its own workspace now points into the project, so ask the agent for the file's full location if it can't find it.
- **Agents can't attach protected files or hard links.** StarNet now refuses some files when an agent sends one to a chat app, attaches one to a web request or uploads one in the browser, and when a routine attaches one to its message, even under FULL POWER: .env files (.env.example and .env.local included), anything inside a .git folder, saved logins and keys (such as .npmrc, .netrc, anything in a .ssh folder or a browser profile), and any file that also has another name on disk (a hard link, which some build tools such as Cargo and pnpm create). Before, such a file in an agent's own workspace could be sent this way, and under FULL POWER a browser upload could reach your SSH keys. The agent is told why. If you mean to share such a file, send it yourself, or for a hard-linked file have the agent copy it to a new ordinary file and send the copy. These checks cover StarNet's own send tools, not commands an agent runs in its terminal.
- **The chat note says why a file wasn't attached.** When an agent sent a file to a chat app and StarNet would not send it (for example, a name that climbs out of the agent's workspace with .., or an empty file), the note in the chat said the file "could not be found in the workspace", even when the file was there. The note now says the file was refused by StarNet's send rules and gives the reason, and the files StarNet now refuses (above) get the same note. A file StarNet could not read, such as one another program holds locked, is named as not attached, with the reason (for example "cannot be read (EBUSY)"). When a routine could not send a picture it had generated (one no longer there, or one StarNet would not send), its note said "It is saved in the workspace on the station"; it now says the picture could not be found, or why it wasn't sent.
- **Files aren't sent from an agent folder that is a link, or from workspaces on a network share.** An agent whose own workspace folder was replaced with a link to another folder (for example, to move it to a bigger drive) keeps working there as before, but nothing in it is sent to chat apps, web requests or browser uploads until you move the folder back or remove the link. A workspaces folder that is itself a link is fine. Nothing is sent either when StarNet's workspaces folder is on a network share (set with `STARNET_WORKSPACES`). The agent is told the reason.
- **Agents upload files to websites only from their own folders.** When an agent uploads a file in the browser, the file must now be in its own workspace or, in a project chat, that project's folder. Before, it could upload any file it was allowed to read: from any folder you had approved, from one you approved when it asked, and with THIS COMPUTER from almost anywhere (under FULL POWER, even SSH keys). StarNet no longer asks you to approve another folder for an upload; it refuses, even with FULL POWER on. To upload a file from somewhere else, such as your Downloads folder, copy it into the project folder you're working in, or open a chat on a folder that holds it (ADD PROJECT FOLDER). In an ordinary chat, an agent can no longer upload from your project folders: open a chat on that project instead.
- **The browser gets a checked copy of each upload.** When an agent uploads a file to a website, the browser now gets a copy of the file StarNet checked. Before each later browser step the agent takes (a click, typing, opening a page), StarNet makes sure the copy hasn't changed; if it has, that step is refused and the agent is asked to select the file again. Each file can be at most 200 MB, and the copy needs as much free space in your temp folder as the file takes. The copy is removed when the agent finishes its reply. If you submit the form yourself after the agent's reply has ended, the file it selected is already gone, so the website gets no file. Ask the agent to submit the form in the same request.
- **A routine attaches the files it made, and names the ones it won't send.** A routine that works in a project folder now attaches the files its reply names from that folder. When its work passes through several agents, each file comes from the run that made it, not from whichever agent's folder held a file with that name. A named file StarNet won't send (see above) is taken out of the message and named in a note after it that gives the reason, which is also written to sidecar.log; before, its ATTACH line was left in the message as written. Files the routine's own agent keeps are sent however old they are. Unless one of the routine's runs recorded making it, a file found in another agent's folder that is older than the routine's run isn't sent, and neither is a name that matches different files in two of its folders. In a routine with a project folder, a file kept only in the agent's own workspace now counts as not found, and its line stays in the message as written.
- **Chat apps show [workspace] instead of where your agents' workspaces are on your computer.** In messages StarNet sends through your Telegram, Discord, Slack, Matrix or Signal connection (replies, routine results, notices, buttons and picture captions), the full path of StarNet's workspaces folder, which usually includes your user name on this computer, now reads [workspace], as in `[workspace]\alpha\report.md`. Other spellings of that folder, such as forward slashes, a Windows short name or %LOCALAPPDATA%, are replaced too. Other folders, such as your project folders, still show as written, COMMS still shows the real path, and messages that leave by other routes, such as STARNET REMOTE or an app you connected in CONNECT, aren't changed.

## Agents working in a project folder

- **In a project chat, your agent can open the files you attach and the files it saves from the browser.** A PDF, video, zip or other file you attached in a project chat, and a screenshot, a page saved as a PDF or a file downloaded in the browser, were kept in the agent's own workspace but named to the agent by a short name, so its file tools looked for them in the project and didn't find them. The agent is now told each file's full location, so it can open, check or send it. A text file you attach is still shown to the agent directly, and the agent is now also told where it's saved, so it can read all of a long one.
- **In a project chat, an agent's terminal opens in the project folder.** A terminal an agent started in a chat that works in a project folder opened in its own workspace while its other commands ran in the project. It now opens in the project, and the agent can start one in any folder inside it while the project is still approved. Unless the agent has FULL POWER, or the run came from your own paired chat that can control this computer, a terminal also won't start inside a .git or credentials folder, or in a folder that is really a link to somewhere outside the workspace and the project, and the agent is told it was refused.
- **On this computer, a `cd` lasts for one reply.** An agent's `cd` in an ordinary chat carried over to its next message and to the same agent's other chats, so one chat could move another chat's commands into a different folder. Each reply now starts in the agent's own workspace, the way project chats already started in their project folder. An agent set to SAFE CELL or REMOTE SSH keeps its folder as before. If an agent assumes it is still in a subfolder from an earlier message, ask it to `cd` again.
- **A GOAL LOOP works in its folder.** A GOAL LOOP set to work in a project folder was told to work there, but its file tools and commands still used the agent's own workspace for short file names. While that folder is still approved, they now use the folder, as a routine's do. After you update, a loop's next pass writes into its folder; notes it saved in the agent's workspace before stay there, so move them into the loop's folder if it needs them.
- **Quests look in the project folder.** A quest in the QUEST LOG that completes when a certain file exists only looked in the agent's own workspace, so a file the agent wrote in a project folder never completed the quest. When the agent works in a project, StarNet now checks that project folder.
- **Files a crew member makes reach the agent that handed it the job.** When your agent handed a job to a crew member, StarNet looked for the files it passed back first in the crew member's own workspace and then in the lead agent's project folder, so they could come back as an older copy with the same name, or as a file from the lead's folder. Each file is now looked up only in the folder that crew member's task worked in, and only a file that is really there is passed on.

## COMMS

- **YOUR FIRST TASK no longer hides the message box.** On a returning station, the first-task panel could cover all of COMMS, message box included, and stay there after you picked a session. It now sits above the message box and steps aside when you pick a session, send a message of your own, an approval reaches you or you press Esc. After you pick a session or press Esc, anything you'd written for it is a press of ↑ away in the message box. It's offered again the next time you open StarNet, until you start a first task (from the panel, or by typing one into the message box once a model is set up) or choose I'll explore on my own.
- **Help me choose a first task no longer keeps your model working after you move on.** When a suggestion took longer than 12 seconds, StarNet stopped waiting for it, but the request to your model kept running in the background. StarNet now ends that request at 12 seconds, or as soon as YOUR FIRST TASK steps aside for you.
- **Your agent's suggestions make room too.** The idea your agent pitches for what to build next and the routines it suggests scheduling now sit above the message box instead of covering it. They step aside, unanswered, when you pick a session, send a message or an approval reaches you, and one that stepped aside isn't offered again until you next open StarNet. If routines were already scheduled when it stepped aside, the line saying whether they'll run stays in COMMS. Esc on your agent's first build idea now counts as choosing something else.
- **The work-profile talk makes room too.** When your agent asks "Want to add more context to your work profile?" and you choose do it now, the talk now sits above the message box instead of covering all of COMMS, so answer its questions in the talk itself. It steps aside when you pick a session, send a message from the message box or an approval reaches you, and can be offered again the next time you open StarNet. Esc closes it, and StarNet doesn't offer it again on its own.
- **One line per burst of tool calls.** When an agent runs two or more tools in a row, COMMS now shows them as one line: the step it's on while it works, then how many steps it took, which tools it used and how long they took (or how many failed). Click the line to see every step. A check mark means the burst finished, and only a burst where every step failed is marked with a red ✗. Group chats fold the same way, and a burst you opened there stays open while the agents keep working.
- **A note you send mid-run reads as yours, and it stays.** A message you hand to a running agent with SEND NOW now shows on your side of COMMS, marked MID-RUN, instead of under the agent's name with a [steering] tag. Once the run has finished, the note stays in the conversation after a reload, at the point where the agent read it.
- **The queue above the message box is easier to read.** A message you type while an agent works sits in a full-width row tagged NEXT, with SEND NOW and cancel keys. After SEND NOW it reads SENT, "read at its next step", until the agent picks it up, and the extra "Sent into the live run" line no longer appears in the chat.
- **Quests finished together share one line.** QUEST COMPLETE lines that land within 10 seconds of each other fold into one ("3 QUESTS COMPLETE · …"), and the QUEST LOG still lists every one.
- **A build's notes and command replies in COMMS read as SYSTEM cards.** When your agent built something while you were away, the notes in that build's own session and the desk prompt now sit together in one SYSTEM card when they come one after another, in larger, brighter text than the old SYSTEM lines, and a row of choices that answers them, such as PLACE ITS DESK, closes the card. A reply to a / command such as /help shows as a SYSTEM card too.
- **A build's saved notes keep their wording and look when you reopen its session.** They show with the same SYSTEM look as when they were live, without the ⚒ ◈ ✕ symbols in front, and the first note no longer ends by telling you to "open this session" while you're already in it. Notes saved before this update are re-worded when they're shown, as plain sentences that start with a capital letter. The build's own card below the notes keeps its ◈ heading.
- **Stop on a new chat's first reply no longer lets a naming call start afterwards.** Pressing Stop during the first reply in a new chat could sometimes let StarNet start one more call to your model afterwards, to name the chat, and that call could rename the chat after you'd stopped it. StarNet no longer starts that call once you've pressed Stop. The chat keeps the name taken from your first message until a later reply finishes and names it as usual.

## Menus, cards and panels

- **A session's right-click menu is cleaner.** Right-click a session in the rail and its menu now has rounder corners and no glowing outline, with a drawn icon beside each item instead of a text symbol.
- **Learned and proposed skills are easier to read.** An agent's learned skills now show as rounded cards with a soft border, with plain counts such as "Used 7 times · viewed 12 · patched 2 · updated Oct 22" and a Read instructions button instead of symbol keys. The revisions it proposes get the same rounded card, with the proposed instructions behind a fold and their details as a short labelled list instead of raw JSON.
- **Many folds now draw StarNet's own arrow.** Folds such as Fine-tune personality in an agent's dossier, Sources StarNet can study for useful work in YOU, Or adapt a starting point and Recent achievements in QUEST LOG, Access & other options and Daily budget & full instructions in AUTOMATE, Connection details in ABILITIES' APPS, Skill details in SKILL MARKET, Inspect tools in TOOLS, Name & technical details in EXTENSIONS, and the folds on a skill revision an agent proposes now draw StarNet's own arrow instead of the browser's ▶, and it turns when the fold opens. Not every fold has changed yet: some, including ones in RECIPES and the RECRUITMENT BAY, still show the browser's ▶.
- **Number boxes in SETTINGS are no longer black glowing wells.** Boxes such as the ones in SPENDING LIMITS now show plain digits on a soft dark field.
- **The tool list in ABILITIES › TOOLS is tidier.** Each entry below the COMPUTE card, such as WEB & BROWSER, has a drawn icon in one column instead of a colour emoji, a plain tag line instead of boxed AVAILABLE and FULL POWER tags, and its switch on the same line as its name. The COMPUTE card keeps its boxed CORE tag.
- **RECIPES and the RECRUITMENT BAY share one main button style.** RECIPES' START SESSION used to be a solid block; both now use the same lit button. Empty lists read calmly: with no API keys saved, the API KEYS line is dim instead of error red, and an empty PROJECTS list says "No projects yet".
- **The WIDGETS picker and TROPHY CASE get the newer look.** The WIDGETS picker has rounder corners, and each trophy in the TROPHY CASE is now a rounded card with a drawn star, with dates like "Oct 13".

## Clearer answers when something goes wrong

- **A model your ChatGPT account can't use now says so.** If you signed in with ChatGPT and picked a model your account isn't allowed to run, COMMS said "Something went wrong on that turn — try again" with a Try again button, and every retry was refused the same way. Now COMMS says ChatGPT won't run that model on your account and offers ▸ PICK A MODEL instead, so you can choose another one from the model dock. (The model dock can still list models your account can't run.)
- **An expired ChatGPT, Grok or Kimi sign-in is no longer counted as connected.** When a sign-in stopped working (for example because another app used the same ChatGPT login), its card in AI & MODELS said SIGN-IN EXPIRED, but routines, chat bots and the `starnet` terminal still counted it as connected. They now count it as expired, and a run on it stops before it starts with a message that the sign-in expired and how to reconnect it under SETTINGS › AI & MODELS.
- **A message that costs too much for one call now says so.** On StarNet credits, when a conversation has grown so long that one more message could cost more than StarNet allows for a single call on that model, COMMS now says so, names the limit StarNet gave, and points to the two fixes: start a fresh chat, or pick a cheaper model from the model dock, which its ▸ PICK A MODEL button opens. Before, it read "Something went wrong on that turn — try again", and trying again was refused the same way.
- **When nothing answers at a local model's address, StarNet stops in seconds.** If Ollama or LM Studio isn't running, or a server on this computer or your local network refuses the connection or its name can't be found, StarNet used to keep retrying for almost two minutes. It now tries once more (after 4 seconds when the name can't be looked up) and stops. The error's detail line, or the error line in the `starnet` terminal, names the address and what to check: start the server, correct its address in SETTINGS › AI & MODELS, or check your network. An online AI service whose name can't be looked up, or that refuses the connection, keeps the almost two minutes of retrying it had in 0.14.1.
- **Image requests on a ChatGPT plan get one more try and a clearer error.** When ChatGPT answered an image request with text and no picture, StarNet blamed the image model ("is gpt-image-2 an image-output model?"). It now tries once more through another ChatGPT model your account offers, and if that also returns no picture, the error quotes what ChatGPT replied and names what was tried.

## Gmail

- **Gmail goes straight to app-password setup.** Google blocks StarNet's own sign-in for full Gmail and Google Drive ("This app is blocked") until StarNet passes Google's review, so in CONNECT those two cards no longer offer a sign-in that can only fail. They're marked "blocked by Google", with one line saying why. On Gmail, SET UP APP PASSWORD opens the Gmail (app password) form, and Google Drive points you to Selected Google files when this computer can use it.
- **The Gmail app-password form starts with your address.** Its two Google links then ask Google to open that account, which helps when your browser is signed in to more than one. When Gmail refuses the login, StarNet now tells apart the causes it recognizes (a wrong or old app password, your Google password used instead of an app password, a sign-in Google paused, IMAP turned off) and gives the fix for each.

## Skills

- **Skill files stay intact after an edit.** Once you or an agent changed a skill you had installed or imported, StarNet saved its other files (references, templates, scripts) to disk as a line of encoded text, so its scripts stopped running, and agents read encoded text instead of the file. Files are now saved exactly as they are, agents read a skill's extra files as text, and a binary file (an image, an archive) is named with its size instead of pasted. A file an earlier version already scrambled reads correctly again and is written back properly the next time an agent uses the skill or it changes, unless it was saved over while scrambled.
- **Approving a skill sticks.** Some skills stayed held back from your agents however often you approved them in CONNECT › ABILITIES › SKILLS, for example an imported skill with a LICENSE file that you or an agent had changed. What you approve and what your agents get now match, so the skill reaches them. If one is still held back after you update, approve it once more.
- **Your edits to a skill's files on disk are kept once you approve them.** When the files of a skill your agents wrote, or one you had already changed, are edited on disk, StarNet holds the skill back until you approve the change in CONNECT › ABILITIES › SKILLS. Approving still left the skill out of your agents' list, and after a restart the old files came back over your edit. The version you approve now becomes the skill. One over the skill size limits is refused with a note to trim it, and nothing is saved.
- **Agents no longer garble code they save into a skill.** When an agent saved a file into a skill, StarNet's key filter could rewrite ordinary code that mentions a password, so a saved script could stop working, and a file over the size limit was cut short without a word. The file is now saved exactly as written, and the agent is told when a file is too big. Keys and passwords are still removed from what agents are shown and from a skill you export, so a line like that can look different there.
- **Skills you install keep their exact text.** StarNet no longer runs its key filter over a skill's text when you install or import it. When an agent changes one part of an installed skill, the lines it didn't touch now stay as they were; before, its first change ran the filter over the whole skill. Keys are removed when the text reaches an agent or leaves in an export. A skill installed with an earlier version keeps any line the filter changed until you update or reinstall it.
- **When an agent removes a file from a skill, it is removed from disk too,** so agents stop getting the old copy. A copy that was changed on disk since StarNet wrote it is left in place. A skill package with an empty file that you install from now on can be updated, exported and rolled back.
- **The skill check reads file names too.** A skill you imported or installed from someone else that has a file named like `eval.py` or `base64.txt` may be held back after its next use, until you approve it once in CONNECT › ABILITIES › SKILLS. In our check, none of StarNet's own Original skills changed.
- **✔ use it on a COMMS skill card approves only the version the card was about.** If the skill's files changed after the card appeared, the card says it could not approve and points you to ABILITIES › SKILLS, where you can read the new version and approve it.
- **Evaluating a PROPOSED REVISION of an installed skill includes its text files.** They were left out of the test run before, so the evaluation now judges the whole skill, which can use a little more of your model budget.

## Memory

- **A changed preference replaces the old memory.** When a new memory contradicts one your agent already holds, like "prefers light mode" after "prefers dark mode", the agent now keeps one memory, the newer one, instead of keeping both or turning the new one away as a near-duplicate. This covers clear-cut cases in English (a choice like dark or light, or tabs or spaces, where something is, or what something is called); other memories are handled as before. Some contradictions are also left as before, such as a memory the agent saves in its own words that contradicts one you gave in yours, or one it saves during a task that has read a web page, an email or other outside content. The old words aren't lost: the memory's card under AGENT DOSSIER › MEMORY › STORED BELIEFS shows "replaced: …", and the REMEMBERED list in COMMS says what it replaced. When a suggestion after a task would change a memory, it's offered as an update and waits for your Keep.
- **A memory that replaced another shows as updated.** In the REMEMBERED list it reads "updated: … (replaced "…")", without the ✕ that undoes a new memory; change or forget it under AGENT DOSSIER › MEMORY instead. Memories that you or your agent corrected before this update show their earlier text on their card the same way.
- **Memory suggestions from a failed run say so.** When a run fails but still leaves something for you to Keep or Discard, its card in COMMS now reads "⚠ from a failed run", and under AGENT DOSSIER › MEMORY › AWAITING YOUR DECISION it shows "⚠ failed run" (lessons from a failed run already did), so you can judge it before you keep it. Suggestions already waiting before the update aren't marked.
- **A run where you turned down an approval teaches less.** If you deny an approval and the run still finishes, StarNet no longer offers follow-up cards from that run's work about what it learned of you, or THREAD ideas to pick up later. It already didn't suggest memories from it.

## In the terminal

- **`/connect` in the terminal.** Type `/connect` in `starnet` to add an AI service without opening SETTINGS. It lists the same services as AI & MODELS, grouped the same way, and shows which ones are already set up. Pick one to sign in (ChatGPT, Grok, Kimi or Claude Code), link StarNet credits, use Ollama on this computer, or paste an API key: the key stays hidden as you type and is checked with the service before StarNet saves it with your other keys. `/connect chatgpt` (or any service's name) goes straight to that one. If ChatGPT, Grok, Kimi or Claude Code is already signed in, `/connect` offers to sign in another account of the same service, the same as ADD ACCOUNT in AI & MODELS.
- **`/usage` shows what each AI service last said is left.** In the terminal, `/usage` now lists each service you've connected and what it last said about how much is left: a Claude Code sign-in's usage limits and when they reset, an API key's rate limits from its most recent call, and your StarNet credit balance. Nothing is estimated: a service that hasn't reported yet shows as unknown, and Grok and Kimi are listed as not saying. Today's and all-time spend are on the last line; the full spending summary, with your spending limits, is still on the STAT page (F1).
- **FLOOR in the terminal.** Press F6 (or type `/floor`) to see your whole crew in one room, drawn with the app's own characters and furniture where your terminal can show images. Working agents sit at their desks, and when an agent hands a job to a worker, the hand-off flies from desk to desk and is written in the floor's LOG. A bigger crew makes the room zoom out, and when even that isn't enough, the view moves to where the work is and each edge says how many agents are out of sight. Where the terminal can't show images, FLOOR shows the same crew as text. Click a name to open that agent's chat.
- **Talk to several agents at once.** In the terminal, `/split <agent>` puts another agent's conversation beside the one you're in, a pane each, each scrolling on its own. Tab or a click picks the one you type to; `/split close` closes the pane you're in and `/split off` goes back to one.

## One station in two windows

- **Two windows on one station keep saving.** With one station open in two windows at once (the app and a browser tab, say), once one window saved, every later save from the other was refused and set aside until you reloaded it. Now that window merges its changes into the station file as it saves: messages both windows added to one session are all kept, and where you changed the same setting, name or crew detail in both windows, the one that saved last wins. It tells you once, shows the other window's changes when you reload it, and names any change it couldn't keep because the other window deleted that session or crew member.
- **Reloading a tab shows that tab's own work.** With the station open in two tabs of one browser, reloading one could bring up the other tab's older copy, with deleted sessions back and renames undone (the station file itself stayed correct). Each tab now keeps its own copy, and changes a closed tab never saved are merged in the next time StarNet opens in that browser.
- **An agent setting changed in one window stays changed.** With the station open in two windows, saving the crew from one could undo a change made in the other, such as an agent's model or FULL POWER. The station now takes only the agents each window changed, and if it doesn't record a FULL POWER change, the message now says why.

## Saving

- **The save dot says what went wrong.** When your latest change hasn't reached the station file, pointing at the dot beside ONLINE now gives the reason (StarNet not answering, the station too big to save, a full disk, a folder that refused the write…), instead of telling you to check disk space whenever saves kept failing. A station too big for the station file (16 MiB) says so on the first try, and warns you if that change is held only in this window.
- **Saves no longer stall behind your agents' ratings.** If a window couldn't catch up on the ratings you gave your agents' work, StarNet refused every save it sent, so the station file stopped updating and an update could be held up. The station now brings such a save up to date itself whenever it can read every rating the window missed.
- **More of your unsaved changes come back after a crash.** When StarNet reopens a window whose last changes never reached the station file, and something else has saved the station since, those changes are now merged in piece by piece (crew, settings, the floor and renames as well as sessions) instead of only its sessions; where both changed the same setting, name or crew detail, the reopened window's change is kept. A change that can't go in because another window deleted that session or crew member is named, and that window's whole save is kept in a copy beside the station file. This covers changes made after you update.
- **Work in a session that already has a restored copy is no longer left out.** When StarNet merges a window's unsaved work back in and a session changed on both sides, it keeps the other side as a "(restored copy)". If that session already had a restored copy, or you had deleted one, later work in it was left out without a word. Now it's added to that copy when it carries on from it, or goes into the next free copy (up to 20 copies of one session, counting ones you deleted), unless you deleted the copy after that work.

## Crashes, quitting and updates

- **When StarNet crashes on Windows, what it started closes too.** If StarNet crashed or was force-closed, its engine and the programs it had started (the browser your agents use, tool servers, commands an agent left running) could keep running in the background. They now end with it. A web page or app your agent opened for you on your screen stays open, but an app started from a command line, such as one launched in a StarNet terminal, can close too.
- **On Windows, background programs your agents start now stop with StarNet.** A server or helper an agent left running in the background now stops when you quit StarNet or its engine restarts. Apps showing a window on your screen are left open, along with their helper programs; the browser your agents use closes with StarNet.
- **START COMPLETELY FRESH and ERASE EVERYTHING no longer mistake another program for StarNet on Windows.** If StarNet had been force-closed and Windows later gave its old process number to another program, START COMPLETELY FRESH, and ERASE EVERYTHING in SETTINGS › APP & BACKUP, could keep refusing because "another StarNet process still owns this station", with no StarNet running. They now check that the program using that number really is the StarNet that held the station.
- **`starnet` starts after the app was force-closed on Windows.** If the app had been force-closed and Windows later gave its old process number to another program, `starnet` could refuse with "its port could not be discovered". It now sees the app is gone and starts StarNet in the background as usual.
- **Windows updates are less likely to stall on "error opening file for writing".** If an older StarNet had left one of its helper programs running, the installer could stop on that message. It now also stops anything still running from StarNet's own program folders before it copies files, and leaves programs elsewhere alone.
- **startup.log says what StarNet stopped.** On Windows, each time StarNet stops its engine, startup.log now lists every program it ended or left running, and why.
- **On a Mac, StarNet's engine now stops when the app is force-quit.** If the app crashed or was force-quit, its engine could keep running in the background until you next opened StarNet. The engine now notices within a few seconds that the app is gone and shuts down properly on its own. On Windows and Mac alike, a station the `starnet` terminal started itself (not the app's own) now also shuts down properly when that terminal is killed, instead of running on in the background.

## SESSIONS and the crew card

- **A calmer SESSIONS list.** On the default COMPACT rows, sessions are now a plain list that lights up under your pointer, and only the open session is a card. A session waiting on you sits on a faint gold fill, and a pinned one shows a small gold bookmark. Session text is sized to suit the station's pixel font at each TEXT SIZE, and a group chat row starts with its title, with its crew's names on the line under it, and their faces too when the list is wide enough. PROJECTS titles and folder lines use the same type sizes.
- **Builds made while you were away look like other sessions.** In SESSIONS their names no longer start with ⚒ and the row shows the time instead of REVIEW. Pointing at the row still tells you a build is waiting for your review.
- **The DOSSIER key is gone from crew cards.** It sat over the portrait, out of line with the names. With two or more agents, right-click an agent's row (or select it and press Shift+F10), or use CREW › AGENTS, to open its dossier. With one agent, clicking the row still opens it.

## Spending

- **The run count in SETTINGS › SPENDING LIMITS counts runs.** On a paid key, the station's own background calls (reflection, study, quest refresh and the like) were added to the "(N runs)" count next to LIFETIME. New ones no longer are, though ones recorded before this update stay in the count. Those calls are now also recorded when they cost $0 on a ChatGPT or Claude subscription, and your dollar totals don't change.
- **A run cut off by a crash no longer counts as fully paid.** If StarNet closed in the middle of a run on a paid key or StarNet credits after a memory search, the next start could treat that run's cost as recorded when part of it never was. Now SETTINGS › SPENDING LIMITS lists it as an interrupted run for you to settle, like any other.

## Routines, work lines and HUD MODE

- **Pause Automation (E-STOP) also stops /v1 runs.** If you turned on StarNet's OpenAI-compatible /v1 API with `STARNET_API_KEY`, a run another program started through it kept working, and spending, after you chose Pause Automation (E-STOP) in the tray menu. It now stops with everything else.
- **HUD MODE can stop a routine's run.** HUD MODE hid STOP WORK and SEND DIRECTION on runs that a routine or a work line started, even though StarNet could stop them. It now shows both, and if the run had already ended when you press STOP WORK, the card says "Nothing to stop: this run had already ended." instead of "Stop requested."
- **A routine whose work line stops early says so.** When a routine handed its work down a line and a later stage failed or ran out of budget, the routine delivered the earlier stage's answer as if the whole line had run. The answer now ends with "⚠ the work line stopped early" and the reason, on schedule and when you press ▶ RUN NOW.
- **▶ SEND A JOB says why a job stopped part-way.** When a job sent with ▶ SEND A JOB or ▶ SEND A REAL JOB stopped because the line used up its LINE BUDGET or its stage limit, it only said the job did not complete cleanly. It now gives the line's own reason, for example that the line reached its dollar limit.
- **A job sent with ▶ SEND A JOB no longer carries earlier jobs' hand-offs.** When you sent a line a job with ▶ SEND A JOB or ▶ SEND A REAL JOB, its later stages also replayed hand-offs from earlier jobs sent that way. That cost extra tokens and could let a stage "remember" work it never did. Each such job now carries only its own hand-offs.
- **STEP THROUGH stays inside the LINE BUDGET.** Each step now gets only what is left of the line's dollar limit, so one step on a priced model can no longer spend far past it.
- **A LINE BUDGET that does nothing is now flagged.** A line has one LINE BUDGET, taken from the first INBOX placed on it that has one, so numbers set on a second INBOX were silently ignored. That INBOX now shows BUDGET NOT USED — SEE FIRST INBOX, and its hover tells you which INBOX's budget is in force.
- **▶ RUN NOW runs a routine the way its schedule does.** A routine with a pre-check script whose prompt starts with / now goes to its agent when you press ▶ RUN NOW, as it does on schedule, instead of running the / command. When StarNet continues an interrupted routine run, it also skips an action in a connected app that the first attempt already recorded (for runs started on this version).
- **A run that broke inside StarNet is no longer recorded as finished.** If a run hit an internal error before it could end normally, run history said it was done, and a quest waiting on it could be marked complete. It is now recorded as an error, and its quests stay open.
- **Runs that looked at an image keep your request as their title.** When an agent opened an image or took a screenshot, its entry in run history could be titled with StarNet's internal screen-capture label instead of what you asked. It now keeps your request as its title.
- **A routine whose folder is gone says so.** If the project folder a routine is set to work in has been deleted or is no longer approved, the routine's row now says "This routine's folder no longer exists, so nothing ran" (or "is no longer an approved project folder") and what to do, instead of "routine workdir must be a currently approved project folder" or a system error that quoted the folder's full path. A routine that runs a script before its agent still shows the older message.

## Chat apps (Telegram, Discord, Slack, Matrix, Signal)

- **Switching AI services no longer sends your key to the wrong one through a chat app.** When you connected a Telegram, Discord, Slack, Matrix or Signal bot on one AI service and then picked a model on another, the bot kept the first service's saved key and address. Its messages could then carry a key to the other service's address. After a restart, for example, StarNet's Anthropic key went to OpenRouter. Reconnecting without pasting a key did the same. Now picking a model on another service, or reconnecting on it, uses a saved key and address only with the service they were saved for. If StarNet holds no key for the new service, the bot stops using the old one, and a reconnect is refused. If you switched services on 0.14.1, pick a model on another service and then your usual one again to clear the old address.
- **A reply a chat app refuses outright is no longer retried forever.** When Telegram, Discord, Slack, Matrix or Signal refused a reply for good (for example, the chat no longer exists), StarNet queued it, retried it on every pass and held back the delayed replies behind it. Now a reply refused that way is noted in sidecar.log and not queued; one refused because the bot's token stopped working is still kept and sent once you reconnect the bot.
- **StarNet doesn't send into a channel that is showing an error.** Agent messages, routine results and notifications now check that the channel is working first, so a channel with a revoked token or a lost connection reports "not connected right now" instead of failing partway through a send. A channel that is still connecting is tried.
- **Telegram approval buttons close once the question is settled anywhere.** If you answered an approval in StarNet or on your phone, if it timed out, or if the run ended, the Telegram message kept live-looking buttons. Now the buttons go away and the message shows the outcome: already answered in StarNet — ALLOWED, DENIED — the action did not run, or no answer in time.
- **A locked file no longer wipes your chats' settings.** If Windows briefly locked the file where StarNet keeps which agent each Telegram, Discord, Slack, Matrix or Signal chat talks to and how it is set up (during an antivirus scan, for example), StarNet could read it as empty and save over it, losing every other chat's settings. Now that save fails instead, and the next one reads the real file.
- **Delayed chat replies keep their code blocks.** A long reply that couldn't be delivered at first and went out later gained stray ``` lines on every retry, and could lose the opening of a code block. It now arrives as written.
- **Turning off or reconnecting Discord, Slack, Matrix or Signal stops the old connection's retries.** The old connection kept retrying delayed replies beside the new one, so a delayed reply could be sent twice.
- **/status in a chat counts the right history.** Its "History: N messages remembered" line now counts what the agent will read on its next reply, and goes back to zero after /new.

## Local models and your own servers

- **Strict chat templates on your own model server stop refusing tasks partway.** On a server added with the CUSTOM card (LM Studio, llama.cpp, vLLM and others), a model with a strict chat template, such as Qwen, could refuse a task partway with "System message must be at the beginning" when StarNet added a note of its own, for example after an empty reply or a tool call written as text. StarNet now sends those notes inside the conversation the way strict templates accept (0.13.5 had already stopped this refusal on the OLLAMA card). Other services that take this chat format, such as OpenRouter, get the new shape too, so on a paid model the first message in a conversation you started before this update may cost slightly more, once, because the service can't reuse what it had cached from that conversation.
- **A chat template that still refuses is named, and StarNet stops sooner.** On the OLLAMA and CUSTOM cards, a model whose template has no system role at all (Gemma-style) now gets one retry in a shape it accepts, and StarNet keeps using that shape until it restarts. If the template still refuses, the turn ends after two tries instead of retrying as if the server were busy (or moves to your first fallback model, if you set FALLBACK MODELS), and the error's detail line names the model, the server and the template's own words, with what to do: pick another model or, for a server on this computer or at a local network address, update the model on that server. (The headline above it doesn't name the template yet.)

## Agents, commands and the web

- **A very long conversation no longer pays to shrink itself over an unrelated error.** In a conversation that started out very large (a long pasted document, many screenshots), StarNet read almost any request the model's service refused as "too long": it could pay for a summary, send the same request again and fail on the same error. A refusal that names its own cause, such as invalid image data, now ends the turn with that error.
- **Look-alike StarNet notes stay plain text.** If a file, web page, email or chat-app message contains tags that copy StarNet's own notes to the agent, such as a steering note or a task list, StarNet now disables those tags before the text reaches the model, so they no longer look like a note from StarNet.
- **A blocked local address no longer costs an agent its tools.** StarNet's web reader refuses private and local addresses such as localhost, and still does. But after that refusal the agent also lost the ability to run commands and to use your saved keys for the rest of the run, as if it had read an untrusted page. Now that happens only when a real web page redirects the agent to a private address.
- **StarNet's browser tries a site's other addresses.** When a website has more than one address and the first one didn't answer (for example on a computer whose IPv6 connection is broken), the station browser (the one in BROWSER that you and your agents share) failed to load it, on an https site with ERR_TUNNEL_CONNECTION_FAILED, even when another address would have answered. It now tries the site's other addresses in turn, and if none answer on an https site, the agent is told that every address was tried.
- **Web search names its own browser when it can't start.** Web search runs a hidden browser of its own. When that browser couldn't start, the message called it the station browser, which read as if browsing itself was broken. Now it says web search's background browser couldn't start and, when Chrome quit right after launch, how it closed, and agents are told the station browser is a separate one they may still be able to use. When the station browser itself can't start because Chrome quit right after launch, its error now includes Chrome's exit code too.
- **A malformed reply to an agent's web fetch can no longer crash StarNet.** When an agent fetched a page or made a web request, one malformed reply from the site could stop StarNet's engine and end every running task. The library behind those requests (undici) is updated with that fix and others.
- **Text a command prints no longer passes for how it ended.** StarNet reads a command's exit code and final folder from a marker it adds to the end of the command. If a file or web page the command printed held a copy of that marker, a failed command could look like it succeeded (including the check script a routine runs before its agent), or the agent's next commands could start in another folder. Each command's marker now carries a random code that printed text can't know. Separately, an agent can no longer name a network share written with forward slashes (`//server/share`) as the folder to run a command in; the `\\server\share` spelling was already refused.
- **Fewer approval prompts when an agent stops or resizes its own terminal.** Resizing, pressing Ctrl-C in or stopping a terminal session the agent started no longer asks for approval each time. Runs you aren't watching, such as routines, chat-app replies and /v1 runs, and runs that have read a web page can now do these too when their agent can use the terminal, so they can stop a terminal session that agent started. Reading or checking a terminal, reading a background command's log and listing the chats the agent can message still ask each time, as before, and so do starting a terminal and typing into it.
- **`STARNET_` settings for background passes work.** `STARNET_AUX_BUDGET`, `STARNET_SKILL_REVIEW`, `STARNET_SKILL_CURATOR`, `STARNET_SCOUT`, `STARNET_THREAD_MINE` and their timeout, interval and spending settings were ignored unless you spelled them `SKYNET_`. Both spellings work now (restart StarNet after changing one), and the `STARNET_` one wins if you set both.
