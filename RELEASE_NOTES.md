# StarNet v0.15.3

On first open after this update, every agent that had Full Access asks first again and FULL BYPASS is off. Their tools, connectors and reach are kept; give Full Access back by hand in each agent's dossier. This release also brings a new dashboard look, a restart that no longer stops on RESUME asking for a key while Claude Code is signed in, a confirmation for anything that gives lasting power, routine runs that no longer fill the session list, and a fix for older chat history that would not load.

## Before you update

- **Agents that had Full Access ask first again, once.** The first time the desktop app opens after the update, every agent that had FULL ACCESS (the FULL POWER working style) is set back to ask first, and FULL BYPASS is turned off. Each agent keeps its reach profile (THIS COMPUTER, TRUSTED PROJECT, REMOTE SSH), its tools and its connectors. Your trusted project folders, other standing Always answers, hooks and plugin approvals, paired phones, the Remote switch, chat-bot owners and routine permissions are kept as they are. One notice names every agent that was lowered; it is shown whole and kept as one entry in the notifications bell. Give Full Access back in each agent's dossier (the FULL POWER key), or turn the station-wide switch back on in SETTINGS › PERMISSIONS under Advanced, where it is titled FULL POWER OVERRIDE (the notice calls it FULL BYPASS); StarNet asks you to confirm each one. Giving Full Access back does not by itself bring back whole-computer reach: an agent whose reach is MY PROJECT FOLDERS (TRUSTED PROJECT) now works without cards only in its own workspace and the project folders you approved (see Permissions and approvals). A station run without the desktop app (`npm start`, pm2, the terminal) is not lowered. If you use both on one station, a Full Access, hook or approval added while it ran without the desktop app is not used when the app next opens it, until you give it in the app; anything removed there stays removed.
- **StarNet can ask once more whether to keep Full Access.** After you give Full Access back, a "StarNet — keep Full Access" dialog can appear the next time StarNet opens, or after a change to the Commander dossier, although nothing about the agent changed. Choose Keep Full Access and it is not asked again. If you say no, that agent asks first until you give Full Access back.
- **Until you give Full Access back, work that relied on it stops to ask or is refused.** That covers routines, the night shift and messages a paired owner sends from a chat app. On Telegram the owner now gets Allow once / Deny buttons in the chat for an agent that asks first; Discord, Slack, Matrix and Signal have no approval buttons, so an ask-first agent's risky steps are refused there.
- **An older "always allow" for every command is retired.** If you answered Always on a command card in an earlier version, that blanket permission is no longer used: each command asks again, one at a time. A short notice says so once when StarNet opens; it is not kept in the notifications bell. Full Access (the FULL POWER key in an agent's dossier) still skips the cards for that agent.
- **Older routine sessions leave the session list on the first start.** Each routine keeps its newest 10 run sessions in the list. Older ones, and saved runs that had nothing to report, leave the list; their transcripts stay on the station, and the routine's HISTORY key in AUTOMATE › SCHEDULES lists its newest 10 runs, where OPEN brings one back. Sessions you typed in, pinned, renamed or that hold deliverables are kept.
- **Routines on a subscription sign-in can now be skipped.** Scheduled work is held, and dropped rather than queued, while the sign-in's usage window is 90% or more used, or after about 2 million weighted tokens of unattended work in 24 hours. Anything you start yourself is never held. Routines and unattended work says where it shows and how to turn it off.
- **Going back to 0.15.0.** 0.15.3 keeps station file format v7. If you go back and later return to 0.15.3, a permission file that 0.15.0 rewrote counts as changed outside StarNet (see Permissions and approvals) and is read as its safe default until you give those permissions again.
- **Coming from 0.14?** This update includes everything in 0.15.0, including its one-way move of the station file to format v7. Read the 0.15.0 notes before updating.

## Permissions and approvals

- **This release includes security fixes.** They change how permissions are stored, given and confirmed, which is why several things below now ask you to confirm. We recommend updating.
- **Anything that gives lasting power asks you to confirm in a StarNet dialog.** Turning on FULL BYPASS, answering a card with Full access or Always, giving an agent FULL ACCESS or a wider reach, pre-approving a permission, trusting a project folder, approving a hook or a plugin, turning on Remote, making a phone or chat-owner pairing code, letting agents use a saved key unattended, switching a toolset back on, turning on build while away, and saving or trying a loop's check command each open a "StarNet — ..." dialog that states what you are allowing. Decline and nothing changes. Lowering or removing anything never asks.
- **Permission files are sealed, and an edit made outside StarNet is not obeyed.** The desktop app seals the files that say what may run without asking: FULL BYPASS, each agent's Full Access, hooks and their approvals, plugin approvals, standing permissions and trusted folders, paired phones, chat-bot owners and routine permissions. A file changed outside StarNet, or an older copy put back, is read as its safe default (every agent asks first, for example), a notice says so, and StarNet keeps the changed file beside it as `<file>.unsealed-<n>`. If the app cannot read its key from the computer's credential store at start, everything holds at the safe defaults and permission changes are refused with the reason until a restart finds the key; nothing is lost. The seal belongs to this computer: a station folder copied to another computer, or opened after the credential-store entry is lost, comes up with none of its permission files used and its routines without their unattended permissions, with a notice, until you give them again there.
- **A command approval covers one exact command.** On a command's card in COMMS the keys are now Approve once, This session, Full access and Deny. Always is gone for commands. This session lets that exact command, with the same folder, time limit and background setting, run again without asking until the session ends, after a confirmation that shows the whole command; a command too long to show whole is approved once only. Cards for other actions still offer Always.
- **Full Access no longer skips protected files or the outside-content lock for commands.** Even with FULL ACCESS or FULL BYPASS, the file tools refuse to write protected files such as `.env` and `.git` internals. After a run has read outside content (a web page, an email, a connector or plugin result), a shell command asks you for that one call when you are watching and is refused when nobody is. A Full Access agent that browses and then runs commands in a routine, the night shift or a Telegram run will have those commands refused.
- **Full Access stays inside the agent's reach.** For an agent whose reach is TRUSTED PROJECT (MY PROJECT FOLDERS), Full Access works without cards only in its own workspace and the project folders you approved; a path outside them asks when you are watching and is refused when you are not. On THIS COMPUTER (MY WHOLE COMPUTER) or STATION GEAR (WHAT I PLACED), Full Access reaches the whole computer; choosing THIS COMPUTER asks you to confirm. A SAFE CELL agent with Full Access is no longer moved onto this computer: its commands are refused with a message naming the two ways out. The dossier and the Permissions page now say what FULL POWER reaches in each case.
- **Editing a Full Access agent asks whether it keeps Full Access.** Changing its instructions (its personality or voice included), model, provider or skills shows a "keep Full Access" confirmation. If you say no, or the change comes from somewhere that cannot confirm (a config import, the terminal, a bridge), the agent asks first from then on.
- **After outside content, risky file writes ask first and name the file.** Once a run has read a web page, an email or another outside source, a write outside its workspace and trusted projects, a write to project instruction or auto-run files (`AGENTS.md`, `CLAUDE.md`, `package.json`, `Makefile` and the like), or to a code file beside a routine's script, asks first. The card names the file and what the run read, and offers only Approve once and Deny; an unattended run is refused. This applies under Full Access too.
- **Other calls after outside content.** A card for a later connector call no longer offers an Always it could not keep: it offers Approve once, Full access and Deny, with one line saying why it asks each time. After reading one web API's response, a run may fetch the next page of that same read without a card; any other call to that service, a request with a body, or a request that attaches workspace files asks when watched and is refused when unattended. Plugin results and a routine notepad written by a run that read outside content now count as outside content, and a failed helper agent's lock carries to the next helper and the lead.
- **Spending limits.** In SETTINGS › SPENDING LIMITS, raising or removing a limit, RESUME on a stopped pool, and booking an unknown charge below the figure it is counted at now ask you to confirm; lowering never asks. On the default daily limit, while one charge is still unknown (after a crash or force quit mid-run), routines, loops, the night shift and other work nobody is watching pause before any paid call until you settle it with COUNT AS; a run you are watching keeps going. The paused routine's toast, session and NEEDS YOU row name the pause.
- **Restoring a recovery bundle does not bring back Full Access, wide reach or unattended permissions.** After a restore every agent asks first, agents on THIS COMPUTER, TRUSTED PROJECT or REMOTE SSH go back to STATION GEAR, routines run without their unattended permissions until you give them again, hook and plugin approvals are asked again, and each chat bot pairs its owner again. The notice says it came from a restore and names who changed.

## Phones, chat apps and the terminal

- **A new phone pairs by the QR code and waits for your approval.** Pairing is proven by the QR code or its COPY LINK; typing the short code alone no longer pairs a phone. A newly paired phone stays switched off until you press APPROVE beside WAITING FOR YOUR APPROVAL in SETTINGS › REMOTE, where the confirmation shows its name and fingerprint. It starts with ALWAYS ASK ticked. Phones paired before the update keep working.
- **From a chat app, an approval is once or no.** Telegram shows only Allow once and Deny (the other chat apps have no approval buttons), and a tap on an older Always or session button is taken as once. A paired owner's messages skip approval cards only when that agent has Full Access or FULL BYPASS is on. A paired phone can still answer once, for this session, or deny; its "for this session" is taken as once for anything that runs (a command, a web request, a click, a message sent). Standing answers are given in the StarNet window.
- **Chat-bot owner pairing is confirmed at the computer.** Making an owner pairing code for Telegram, an agent's own bot, Discord, Slack, Matrix or Signal asks you to confirm, and who owns each bot is kept in a sealed record. Owners already saved are sealed as they are on the first open after updating.
- **Terminal: standing answers are confirmed, or applied once.** In the `starnet` terminal, ALWAYS on a card is applied once with a note saying where to confirm it, unless that terminal started the station; commands no longer offer ALWAYS. `/yolo` and Full power in terminal setup are confirmed, or you are told Full power was not given and where to give it. Editors (ACP) and MCP clients are offered a command once or reject.
- **A station run without the desktop app confirms with a six-digit code from its own console.** On `npm start`, the `starnet` terminal or pm2, the confirmations above ask for a code the station prints only in its own terminal. Five wrong codes lock permission changes for 15 minutes, doubling up to a day and kept across restarts. Stopping the station over the API asks too. Under pm2 or a redirected log the code is not written to the log unless the station is started with `STARNET_DESK_CODE_TO_LOG=1`.
- **Terminal `/usage` shows StarNet's own tokens per plan window.** Under each subscription sign-in it prints how many tokens this station used since each window opened, never a percentage. Every model call now leaves one usage record on the station: counts and ids, never prompt or reply text.

## Routines and unattended work

- **Unattended work on a subscription sign-in is held near the plan's limit.** This is on by default. Scheduled routine fires, night-shift jobs, goal loops, away builds and triggers wait when the sign-in's usage window is 90% or more used, and pause after about 2 million weighted tokens of unattended work in 24 hours. Anything you start yourself (a message, RUN NOW) is never held. A held start is dropped, not queued: the next one comes on its normal schedule. The routine's row shows held with the reason, SETTINGS › AUTONOMY says when it lifts, and pressing SMALL JOBS or FREE under ON ITS OWN restarts the 24-hour count. A metered API key keeps its dollar limits. With no window reading from the provider the 90% line never holds; the 24-hour count still applies, because it uses StarNet's own token records. Setting `STARNET_UNATTENDED_WINDOW_PCT` or `STARNET_UNATTENDED_RAIL_TOKENS` to 0 turns that line off.
- **A routine's unattended permissions are confirmed, and editing the routine asks whether to keep them.** Letting a routine use the terminal, connected tools or images with nobody watching asks you to confirm. Editing what a granted routine runs (its task, script, agent, folder, toolsets, skills, model or provider) asks again; if you decline, the form offers SAVE WITHOUT ITS PERMISSIONS. A rename, a schedule change or a delivery change keeps them.
- **A granted routine's script that changed will not run until you allow the new version.** The routine shows a "script changed" badge, and ALLOW THIS VERSION shows the new script and asks you to confirm it.
- **A granted routine keeps its permissions only on the model and instructions you confirmed.** If the agent's model, provider or instructions (its personality or voice included), or the routine's skills, are not what they were when you said yes, that run goes ahead without its permissions. A run that holds unattended permissions also never falls back to a different model or provider: it keeps only other keys or sign-ins for the same model, so if the confirmed model cannot answer, the run fails instead of moving to your fallback. A granted run also no longer receives your Commander dossier, active goal, recalled memory or house-rule files. Turning the agent's Full Access on or off does not drop the permissions.
- **Routine runs no longer fill the session list.** A script-only check that passes makes no session, and a run that succeeded with nothing to report keeps none; a failed check still makes one. A run you have not opened that failed, asked something or did not finish stays in the list and in NEEDS YOU until you open it, up to 10 per routine beyond its newest 10. Sessions you deleted stay deleted after a restart: the station now remembers 20,000 deleted sessions, was 500.
- **Routine rows say what happened.** In AUTOMATE › SCHEDULES a routine's last result can read held, with the reason, or "line stopped" where it used to show a green ok, and the same verdict is read by `/routine`, the agent's routines tool and the phone. A row shows "~N weighted tokens a fire" once a scheduled fire is recorded, and the night-shift panel shows the figure per job.
- **The night shift stops re-proposing a build that is already waiting on your desk.** When an away job only proposed a build you have not kept or discarded yet, the next jobs are held before they spend anything, and SETTINGS › AUTONOMY says it is waiting on your verdict and names the build. A verdict, a new message, or a change of goal, priority or autonomy setting releases it.
- **Long scheduled runs are no longer treated as dead, and a retry does not repeat its sends.** A routine inside one long tool call, streaming only text, or running when the computer slept keeps its run. A retry after a temporary failure reuses the first attempt's identity, so connector writes already made are not sent twice.
- **A station set up from the terminal runs its routines.** A station set up with the terminal and never opened in the app refused every routine, channel message and line with "the saved floor is invalid". New terminal setups now save correctly. A station already in that state from 0.15.0 says to open StarNet once to finish setting it up.

## Restart, sign-in and history

- **The app no longer opens on RESUME "Enter your key" while Claude Code is signed in.** On start StarNet waits, up to 20 seconds, for the station's sign-in check before deciding to show RESUME, and the boot screen says "checking CLAUDE CODE sign-in" while it waits. If RESUME does open first, it re-checks for up to a minute and goes in by itself once the sign-in is confirmed, as long as you have not touched the screen. The banner says what is really missing, and asks for a key only when the saved provider uses one.
- **RETRY AUTO-RESUME, RESUME STATION and RESTORE BACKUP can no longer overtake each other.** Only one of the three acts at a time, so the station opens exactly once. Before, pressing RETRY AUTO-RESUME while RESUME STATION was still testing the connection could resume the station and then replace the saved Overseer with a new one.
- **Chat history from before 0.15.0 loads again** (GitHub #178). A long conversation written on 0.14 could show "Conversation history could not be restored" on every open and hold every message. The station now reads the old history through once on the first open and remembers the result.
- **A message cut off by a crash no longer locks the chat.** If StarNet stopped while saving a message, the half-written last line is moved to a `.torn-` file beside the history and the chat loads without it, saying once: "The last unfinished message was set aside: StarNet stopped before it finished saving it." When history cannot be restored, COMMS now says whether trying again can help, or to restart StarNet once and report it with SETTINGS › APP & BACKUP › COPY DIAGNOSTICS.
- **Mac: a first run stopped during the wire test comes back to its setup** (GitHub #181). If macOS stops StarNet's display while WAKE is testing the connection, the setup screen returns with your name, provider, model, character and voice kept and a line saying what happened. The key is not kept, and Working style comes back as ASK FOR APPROVAL; the message says where to choose FULL POWER again. Why macOS stops the display is not found yet.

## Runs and models

- **Saying "yes" or "ok" to an agent's offer starts the work.** A short yes after the agent closed its reply by offering to do something ("I can write that script for you.") now runs as a task with tools even when the offer was not a question. After a refusal, a hedge or a condition, the same "ok" stays a chat reply. Known misses are under Known issues.
- **Calls held by the Task Brief are made again instead of being reported as done** (GitHub #187). When the brief held a file write or a command, the reply that settles the brief now lists those calls and says nothing has run yet, so the agent makes them before it reports. When the model sends the brief and its first write together, both now go through in one step.
- **Long command and tool output keeps its end.** When a shell command, a check or a connector result is too long, the agent now gets the first 70% and the last 30% with the gap marked, where it used to get only the beginning.
- **A tool call that never stops writing is stopped and named.** If a model keeps writing the arguments of one tool call past 1 MB, or for more than 10 minutes on a hosted model, StarNet stops it, does not run the half-written call, does not retry, and says which tool and how much was written. A local model is limited by size only.
- **Delegated workers report what really happened** (GitHub #177). Each worker's result says whether it finished, was stopped, was cut short or failed, and a worker that could not start shows "couldn't start:" with the real reason on its card and in NEEDS YOU.
- **Effort settings say what they do.** On the Claude Code sign-in, `/reasoning` and `/fast` now add "Note: Claude Code runs your messages on its own default effort, so this setting does not change them." In the model dock, the reasoning-effort tooltip adds "uses noticeably more of your usage" on xhigh and max for providers that receive the setting (not on the Claude Code sign-in), and marks "the default" on the level your provider really runs at when nothing was chosen.
- **A new OpenRouter setup is prefilled with Opus 5.5** when OpenRouter's live model list includes it. A model you already chose is never changed.
- **Session titles and background passes use the provider family's small model.** This is on by default. Naming a new session, and the study, thread-mining and scout passes, run on the small model of the same provider family when the provider lists one; reflection stays on your model, and your own aux model setting still wins. On your own API key you will see a second, smaller model in your provider's usage. The skill review now runs only after a run that held a correction, a failed tool call, a new multi-step procedure or a thumbs verdict, and learning passes wait longer after a pass that kept nothing; "remember", "always", "never" or "from now on" in your message skips the wait. `STARNET_AUX_SMALL_MODEL=0` turns the small model off. We claim no saving from any of this.
- **Follow-up messages carry earlier tool results as a short opening plus a saved file.** This is on by default. In a resumed terminal chat, a queued follow-up and chat-app conversations, a long tool result from an earlier message is sent as its first 240 characters and a pointer to a saved copy the agent can read back. `STARNET_CROSS_RUN_REPLAY=0` turns it off.
- **StarNet Credits messages say what happened** (GitHub #182). A refusal for credits no longer blames your provider's billing: it says nothing was charged and either that part of your balance is held by unfinished calls, or to top up under SETTINGS › AI & MODELS. When StarNet's relay reports an outage on its own side, the message reads "StarNet's model supply is temporarily out; your credits are untouched. Try again in a few minutes." When the account cannot be read, the card offers UNLINK beside RETRY. On a station not linked yet, an agent's model list shows a STARNET CREDITS row and a LINK STARNET CREDITS button.
- **Image generation can keep your real product in the picture.** Give an agent a photo file of the real item and it can pass it to the image tool as the product to keep, with only the scene changed; a style reference can be given beside it. Where the image route cannot carry the photo (DALL-E, a GIF, a connection with no image-edit endpoint), or the photo is a web address and not a file, the call is refused and nothing is drawn. The result still needs a look before you show it as the real product.
- **Gmail (app password): an HTML email returns what it says.** Reading a message now returns the HTML part's text, with image alt text, when the plain-text part is empty or only a stub; before, some newsletters came back as a few links or the footer. The result says which part was read.

## Shell, browser and remote machines

- **The shell refuses a working-folder program that shadows an everyday tool.** On Windows, if the folder a command runs in holds its own file named like an everyday tool that would run in place of the real one on PATH, the command is refused with a message naming the file. The guarded names are git, gh, rg, grep, findstr, where, node, npm, npx, pnpm, yarn, bun, deno, python, python3, py, pip, pip3, uv, curl, wget, ssh, scp, tar, powershell, pwsh, cmd, code, cargo, rustc, go, dotnet, java, javac, winget and choco. A project's own script that shares no name with those tools (`make.bat`, `gradlew`, `build.bat`) still runs.
- **Python 3.14 Install Manager commands run again** (GitHub #184). On Windows, `python`, `python3` and `py` installed by the Python Install Manager were refused by the shell guard. They now run; `pythonw` is still refused as a windowed program.
- **The shell protects StarNet's own permission files.** A command that names StarNet's own hook, approval, roster or seal files is refused. A project's own `hooks.json` still runs when it is named by a plain path; see Known issues for forms the check cannot resolve.
- **Sign-ins in the station browser last.** Sites you sign in to stay signed in across restarts, including where "stay signed in" was not ticked. A run that cannot use the main browser profile because the station browser window is open gets a copy of your saved sign-ins, and a leftover browser is asked to close before it is ended so recent sign-ins are not lost.
- **Remote SSH agents.** Full Access on an agent whose reach is REMOTE SSH (ANOTHER MACHINE) stays on that machine and gives nothing on this computer. Workspace sync moves only changed files, and a command whose connection drops says its outcome is unknown. On a REMOTE SSH agent that asks first, a command may name absolute paths only inside its workspace on the remote machine (standard device files and system program folders still work); `~`, `$HOME` and a bare `cd` are refused with a message saying so. Full Access lifts this on that machine only. Remote checkpoints now keep the newest 10 and older ones are removed (`STARNET_SSH_CHECKPOINT_KEEP` changes the number).
- **A busy computer no longer locks your own browser out of the station page.** When StarNet is opened in a browser, the ownership check is retried once with a longer limit, and while the page's key is withheld a bar across the top says why, with Check again and Hide. The desktop app is not affected.

## The dashboard

- **A new dashboard look.** CREW, COMMS, the top bar, the bottom dock and every window that rises from the dock are drawn as one device with dark glass screens, in whichever PHOSPHOR THEME colour you use. The floor is not tinted or changed. The look itself adds and removes nothing; the few controls that moved or were renamed are listed in the bullets below. HUD mode keeps its own look.
- **CREW and COMMS.** The title bars are name plates, the session list shows a status light per session, and the composer is one command line over a row of keys with SEND as the lit key. The cards inside a conversation, NEEDS YOU, DELIVERABLES and the dossier's BRIEF and GROWTH wear the look too. The "+ NEW" session key is now a round "+" at the end of the SESSIONS | PROJECTS strip.
- **Crew portraits are a round lens.** Each agent's picture in the CREW list shows the face close up, with the status light on the ring. The lens lights while that agent works and while it waits on you.
- **The model list stays inside COMMS.** With COMMS dragged narrow, the model list is held to the width of COMMS instead of hanging out past its edge, and the keys in its footer wrap onto a second line at a large TEXT SIZE.
- **Pop-up pieces match.** The live voice panel, the crate card, the quit guard, the save banners, the tutorial coach, the image viewer, the model list, the slash-command and agent lists, toasts, the boot and title screens and Build Mode are in the same look.
- **BRIGHTNESS darkens the whole dashboard.** In SETTINGS › LOOK & SOUND, under CUSTOM PHOSPHOR, sliding BRIGHTNESS below 0 takes the dashboard down to nearly black at the far end, and the keys switch to lit labels so they stay readable.
- **AI & MODELS folds the providers you have not set up.** Once one provider is set up, the others in each group sit behind one strip that names them and reads, for example, "5 NOT SET UP"; click it to open them. A new station still shows every card.
- **AUTOMATE, RECIPES and PROGRESS.** In AUTOMATE each of SCHEDULES, GOAL LOOPS and AWAY WORK is one screen with no second side menu: the list carries a + NEW SCHEDULE or + NEW GOAL LOOP key, the form carries the way back, and ON ITS OWN with its CHANGE key is a strip across the top. A RECIPES row is its seal and its name, with the description on hover. In PROGRESS, "Station systems" is a fold that reads "N OF M ONLINE" and rests closed once everything is online.
- **Lighter drawing turns on by itself on slower machines.** On a machine StarNet judges slow (no WebGL or a software renderer, an Intel-graphics Mac, old Intel HD graphics, 4 or fewer processor cores, or a floor it measures as struggling), panels lose their background blur, conversation text loses its glow, and the floor pauses drawing while you scroll a panel. The system's reduced-transparency setting turns on the first two; its reduced-motion setting turns on the scroll pause. Scrolling up through a long conversation also does less work per step on every machine.
- **A new crew skin, Minion,** is in the skin picker. In Build Mode, picking a prop now lights only the tile you picked.

## Updates

- **From this version on, an update must carry StarNet's own code signature before it installs.** The app checks the download's Windows publisher signature, or the Apple Developer ID signature on a Mac, on top of the existing updater signature. A download that fails is refused in the Update Center and nothing is installed. Linux keeps the updater signature only. The check runs in the installed copy, so it first acts on the update after this one. If a later update is refused for its signature, nothing is installed or changed: use DOWNLOAD LATEST MANUALLY in the Update Center, or download it from the website.
- **Mac: the in-app update works when StarNet is on a different disk.** The app now stages the update beside itself. If StarNet is running from the disk image or the Downloads folder, or on a read-only disk, it refuses before downloading and says to quit, drag StarNet into Applications, open it from there and install again.

## Off unless turned on

- **A set of prompt and caching experiments ships switched off.** They sit behind `STARNET_*` environment switches that read as off when unset: prompt layout and caching changes, compact Claude Code tool text, smaller model defaults on the summon card (`STARNET_CREW_DEFAULTS`), sending the reasoning effort you chose to Claude Code (`STARNET_CLI_EFFORT`), and letting look-only commands such as `ls` and `git status` run before the Task Brief is settled (`STARNET_BRIEF_READONLY_SHELL`). There is no switch for them in the app, nothing changes unless you set one, and we claim no saving from any of them.

## Known issues

- **A few pieces still wear the old look, and no setting brings the old look back.** The GitHub sign-in code dialog, the "STATION FAILED TO BOOT" banner, hint bubbles that open away from the dock, and a pinned widget's readings and its drag ghost are not converted yet.
- **Lighter drawing has no switch in SETTINGS.** Any computer that reports 4 or fewer processor cores, Windows included, gets the flatter look after updating.
- **RESUME.** RESUME can still appear for a few seconds after the station's sign-in check has settled, and its banner is not repainted while RESUME STATION is testing. After a backup that restores only partly, RESUME STATION still opens the old save while RETRY AUTO-RESUME opens the restored one.
- **A routine that ran without its unattended permissions does not say so on any page.** If an agent's model, provider, instructions, voice or personality, or the routine's skills, changed since you confirmed them, the run goes ahead without them and the reason is written only to the run's record. Give the permissions again by editing the routine in AUTOMATE › SCHEDULES.
- **The notice naming the agents that were lowered can be missed.** It is shown when the station opens for the first time after the update. If that first open stops on RESUME or a recovery screen and you quit there, later opens show only a short "still ask first" line. The agents are lowered either way: check each dossier.
- **"yes" and "ok" still miss some offers.** An offer whose verb is outside the known list (restart, merge, upload, commit, push, edit, review and others) or shaped "I can't X, but I can Y" still reads as chat, and some status lines ("Now I can ...", "I could run the tests and they pass") still read as offers. An offer made in the middle of a reply, not at its end, still reads as chat. A bare "ok" or "yes" after a general sign-off ("Let me know if you'd like me to make any changes.") can start a work run where 0.15.0 treated it as chat. In a chat app, a "yes please" to an offer runs with tools but is reported as chat and places no crate.
- **The Task Brief fix relies on the model following the note.** If you answer No to a question the agent asked in the same reply as a write, or send No while the run is still working (a mid-run message, or from Telegram), the agent can still be told to make the held call. "Nothing has run yet" can be said beside a result in the same reply.
- **Helper hand-offs.** The hand-off names a failed helper's saved files by bare names the next helper may not be able to open, and labels helpers that hit a limit, asked a question or came back empty as FAILED.
- **The shell refuses some legitimate forms.** A command that reaches `hooks.json` through something the check cannot resolve (`awk '{print $1}' hooks.json`, `cat $REPO/hooks.json`) is refused: use the plain path. A project that ships its own wrapper named like a guarded tool (a local `node.cmd` or `npm.cmd`) is refused while a real one is on PATH.
- **Some damaged history stays refused.** Only a cut-off last line is set aside. A history file an older version left with a broken line in the middle is still refused.
- **Mac on 0.15.0 or older, installed on a different disk.** The update to 0.15.3 is installed by the version you already have, so "cross device link" can still stop it. Move StarNet into Applications and install again, or download 0.15.3 from the website.
