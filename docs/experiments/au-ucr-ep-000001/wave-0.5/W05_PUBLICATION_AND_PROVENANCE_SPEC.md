## 3. Identity domains

The publication system must keep these identities separate:

1. `raw-working-tree-sha256-v1`: exact checkout bytes, byte count, line-ending counts, capture
   platform/time and worktree status.
2. `crlf-to-lf-sha256-v1`: only CRLF-to-LF transformed bytes, transformed byte count and SHA-256.
3. `git-blob-oid-v1`: exact blob bytes, repository object format, full blob OID, size and an
   independent SHA-256 of blob bytes.
4. `git-index-path-binding-v1`: stage-0 path, mode and blob OID; this is not a commit binding.
5. `git-commit-path-binding-v1`: repository-relative path, full commit OID, containing tree OID,
   mode and blob OID.
6. `candidate-manifest-identity-v1`: canonical manifest bytes and their external SHA-256.
7. `publication-receipt-identity-v1`: exact canonical receipt bytes, signer/authority evidence,
   publication locator and immutable timestamp or transparency evidence.
8. Repository identity: canonical remote URI plus an approved stable repository identifier.
   A local path, branch name or remote URL alone is not immutable identity.

Equality across domains must be measured and recorded. It must never be inferred from matching
filenames, a clean status, a branch name, a hash prefix or line-ending configuration.

## 4. Candidate manifest design

The immutable candidate manifest is a UTF-8 JSON document, without BOM, serialized under one
versioned canonicalization profile such as RFC 8785. The profile itself must be named and
digest-pinned. It must reject duplicate keys, duplicate paths, absolute paths, `.`/`..` path
components, backslash separators, case-colliding paths and entries outside the declared root.

Required manifest-level fields:

- schema ID/version and canonicalization profile;
- experiment, work request and candidate IDs;
- canonical repository identity and canonical remote URI;
- Git object format;
- full candidate commit OID and root tree OID;
- parent OID set;
- candidate path root;
- generation UTC time and generator identity/version;
- exact sorted-entry rule (ascending UTF-8 repository-relative path bytes);
- entry count generated by authorized freeze enumeration (the earlier Wave 0.4 observation was
  20, but that number is not consumed as a normative expected count);
- hash-domain declaration `crlf-to-lf-sha256-v1`;
- unsupported-reference disposition preserving the exact value above;
- prerequisite manifest/receipt IDs; and
- an external `sha256` over the final canonical manifest bytes.

Each entry must contain:

- repository-relative path and media/schema type;
- normalized byte count and SHA-256;
- raw observation byte count and SHA-256, clearly marked non-portable;
- Git mode, full blob OID, blob byte count and blob SHA-256;
- full containing commit OID and containing tree OID; and
- an explicit result showing whether normalized working-tree bytes equal blob bytes.

The manifest cannot securely contain an ordinary digest of its own final bytes. Its final digest
must be carried by the publication receipt, signed envelope, transparency record, or containing
Git object whose identity is itself recorded externally.

## 5. Candidate freezing procedure

An authorized publisher must:

1. freeze the 20 intended paths and reject concurrent byte changes;
2. generate and independently reproduce all raw and LF-normalized measurements;
3. stage only the authorized candidate paths without changing historical artifacts;
4. obtain index path bindings and verify staged blob bytes against every manifest entry;
5. create a candidate commit only under explicit commit authority;
6. regenerate commit/tree/path bindings from the resulting commit;
7. finalize the canonical manifest, then place it in a separately authorized containing commit
   or immutable signed envelope;
8. independently verify the exact commit, tree, blobs, manifest digest, repository identity and
   entry count;
9. push the exact objects only under explicit push/publication authority;
10. verify remote object reachability and immutable locator;
11. issue a publication receipt; and
12. preserve failed or superseded attempts append-only.

A commit created before the manifest knows its own commit cannot contain a manifest that truthfully
names that same containing commit without a cycle. The implementation must use either a two-commit
model (candidate-content commit, then manifest commit) or an external immutable envelope. Both
commit OIDs and their roles must be explicit.

## 6. Publication receipt design

The receipt must bind:

- canonical repository identity and immutable publication service/namespace;
- exact candidate-content commit and root tree OIDs;
- exact manifest-containing commit or external envelope identity;
- manifest canonical-byte SHA-256 and byte count;
- all dynamically enumerated path/blob bindings, directly or by the verified manifest digest;
- object format and full, non-abbreviated object IDs;
- pushed ref only as discoverability metadata, never as identity;
- remote verification time and method;
- publisher stable identity, mandate/delegation, scope and acknowledgement;
- signature algorithm, key/certificate identity, validity/revocation evidence and signature;
- transparency/timestamp locator when required;
- predecessor and supersession relationships; and
- an explicit statement of whether this is publication only or also a separate acceptance.

Publication failure, ref movement, object loss, key revocation, manifest mismatch or authorization
failure must suspend dependent decisions and produce an append-only revocation/correction receipt.

## 7. Acceptance binding

An acceptance receipt is valid only if an effectively assigned Decision Chair signs or otherwise
authenticates a decision that names:

- the canonical repository identity;
- the exact candidate-content commit and root tree;
- the exact manifest identity and publication receipt identity;
- the exact freeze-generated entry set and all manifest bytes through the manifest digest;
- the review/QA/finding-closure receipts on which the decision depends;
- decision scope, effective time, expiry/revocation and conditions; and
- the accepted revision without branch-name substitution.

Changing any candidate byte produces a different normalized digest and normally a different Git
blob/tree/commit. Any such change requires a new manifest, publication receipt, review disposition
and acceptance decision. Acceptance of a path, branch, PR, nearby revision or same-prefix object
does not accept these exact bytes.

Publication and acceptance are distinct. Neither one authorizes implementation, construction,
testing or execution; G4 still requires a separate exact-run release.
