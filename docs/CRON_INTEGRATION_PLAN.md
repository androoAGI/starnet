## 1. Preamble — what we are borrowing and the prime directive

the reference harness fires scheduled agent runs through a **single-pass `tick()`** (`scheduler.py:1970`) that the gateway calls every 60s from a background thread (`scheduler.py:5`): it takes a file lock, computes due jobs via `jobs.get_due_jobs` (`jobs.py:1032`), advances each job's `next_run_at` **before** execution for at-most-once (`scheduler.py:2017-2018`), and runs each job **in-process** by constructing `AIAgent(...)` and dispatching `agent.run_conversation(prompt)` onto a per-job `ThreadPoolExecutor(max_workers=1)` worker with a contextvars-copied context + an inactivity-poll loop (`scheduler.py:1781-1786`) — in-process is the load-bearing fact (no subprocess, no HTTP, no IPC), but the call is wrapped in `concurrent.futures` threads, not run on the ticker thread. The schedule math is pure (`jobs.parse_schedule` `:206-292`, `jobs.compute_next_run` `:373-416`); the wall-clock timer lives in the gateway, not the scheduler. Unattended consent is a config-gated, default-deny posture under an unconditional hardline floor (`approval.py:1116-1155`). Job state persists to `~/.ref-harness/cron/jobs.json` with atomic temp+rename (`jobs.py:471-487`).

We are **mining this for patterns, not porting it.** The prime directive, in four clauses:

1. **It is a pattern mine, not a port.** We take the *shape* of an idea (a single-pass tick over pure due-job math; advance-before-run at-most-once; fast-forward-not-replay missed runs; a per-job in-flight lock; default-deny unattended consent under a hardline floor; an atomic versioned job store; a typed-slot blueprint catalog that emits the one real create-job; an anti-nag suggestion store) and re-derive the *smallest honest version* against our seams. We leave behind every ref-ecosystem artifact: the `ThreadPoolExecutor` parallel/sequential pool split, the `croniter` dependency, IANA `ZoneInfo` resolution + the env/config tz cascade + the cache, the `child_process` script-preprocessor + its path-jail + redaction + downgraded injection scanner, the `REF-HARNESS_CRON_SESSION`/`REF-HARNESS_CRON_AUTO_DELIVER_*` contextvar dance, the `_HOME_TARGET_ENV_VARS`/`_KNOWN_DELIVERY_PLATFORMS`/`Platform` enum delivery matrix, the 14-entry lifestyle blueprint catalog, the four-renderer (form/slash/deep-link/docs) sprawl, the cross-process `.tick.lock` (fcntl/msvcrt), and the threading/asyncio machinery.

2. **Node, not Python.** Our loop is single-threaded async with real I/O concurrency. There is no GIL, no `threading.Lock`, no `ThreadPoolExecutor`, no `as_completed` fan-out, no `asyncio.run` delivery coros, no fcntl/msvcrt file lock. A `setInterval` timer in the one ambient-I/O module + a `Set` of in-flight runIds + a `Map` is the whole concurrency mechanism. The Python "parallel pool vs sequential workdir pool" collapses to simple in-process serial dispatch through the one `runOnce` host.

3. **Nothing violates the existing discipline.** Every new module is UMD, zero-dependency, headless-testable with injected deps (an injected `clock` so no test ever reads the wall clock), deterministic (no bare `Math.random`/`Date.now`; `lint-determinism.js` scans `shared/` + `sidecar/`, excluding only `sidecar/index.js` — confirmed `lint-determinism.js:11,16,35`). **Every cross-boundary signal goes through `shared/events.js` + `shared/emitter.js` first — a new schema rung *before* any producer**, or `emitter.js` drops it (`emitter.js:17,20-23`) and `lint-emits.js` flags the literal `emit` (`lint-emits.js:37,45`). Every persisted shape is save-safe (versioned, atomic temp+rename, tolerate missing/corrupt → fail-closed). One step = one revertable commit, ≤3 files, gating test first, fast suite green (`< ~10s`) before the next.

4. **Nothing jumps the critical path.** Cron **is** roadmap step **1.7 triggers** (`REF_HARNESS_INTEGRATION_PLAN.md:19` names the Phase-1 spine `1.0 keychain → 1.5 consent → 1.6 PROPTERM → 1.7 triggers → 1.8 recovery/kill-switch`). The `'schedule'` trigger is **already frozen**: `shared/events.js:24-26` enumerates `agent.run.start.trigger ∈ ['directive','schedule','event']`, and `loop.js:115` already reads `const trigger = o.trigger || 'directive'` and emits it at `loop.js:125`. So a scheduled run is a *first-class, already-frozen* concept — the trigger contract predates its first scheduled producer. The genuinely-new signals are the *cron lifecycle* rungs (`cron.*`), which get their `shared/events.js` entry first. Cron rides the run host `runOnce` — **today still the monolithic inline core at `index.js:184-281`; `runOnce` does not exist yet** (grep: zero matches), so its extraction is a hard prerequisite performed by `MESSAGING_INTEGRATION_PLAN.md` Commit 4 **or**, if that hasn't shipped, by CRON **Commit 4a** (§5) — and the **existing** consent machinery (`surface:'autonomous'`, the fail-closed floor). It forks neither the loop nor the event contract.

## 3. The design

### 3.0 Shape, end to end

```
sidecar/index.js  ── setInterval(60s) ──► tick(now = Date.now())          [the ONE ambient timer + now-source]
   (composition root, lint-exempt)            │
                                              ▼
                              cron-math (sidecar/cron.js — PURE, injected clock)
                                 • planTick(jobs, now) -> { fire[], skipped[{jobId,reason}], next[{jobId,nextAt}] }
                                 • dueJobs / nextFireAt / parseSchedule    (no Date.now, no setTimeout, no rng)
                                              │  returns DATA (which jobs fire + the advanced next-fire to persist)
                                              ▼
                              index.js applies the plan (the side effects):
                                 • advance nextRunAt BEFORE run (at-most-once), persist via atomic temp+rename
                                 • check the in-flight Set (one-run-per-job lock); emit cron.skipped if locked
                                 • for each fired job: mint runId (crypto.randomUUID), build runSpec from the stored job
                                              │  { key (boot-frozen), model, system, messages, agentId, isTask, surface:'autonomous', trigger:'schedule' }
                                              ▼
                              runOnce(...)  (index.js — the SAME run host the browser uses)
                                 • runAgentLoop → frozen agent.* events on an in-process emit sink
                                 • surface:'autonomous' ⇒ ungranted mutation default-denies (permissions.js:92)
                                              │  buffer agent.token by runId; watch agent.run.end / .error
                                              ▼
                              DELIVERY (reuse the channels seam + deliverable + notify):
                                 • [SILENT] strict-equals check on the buffered reply  ── suppresses delivery, keeps audit
                                 • deliver=channel → adapter.send (chunked) + channel.delivery rung
                                 • deliver=local   → fs.*/notebook.write deliverable file (agent's own tools)
                                 • in-app cue     → notify rung; cron.result {jobId,runId,outcome}
```

The cron-math module never imports the loop, the provider, the broker, or `fs`. The **`index.js` tick driver** is the analogue of the reference harness's gateway 60s thread + `tick()` executor: the one seam where wall-clock time drives the pure plan, which drives the existing run host.

### 3.1 The PURE cron-math module vs the index.js-owned TIMER + now (the determinism split — load-bearing)

This split is the spine of the whole subsystem and is dictated by `lint-determinism.js`. The lint's exact scan set is `ROOTS = ['shared','sidecar']` (`lint-determinism.js:11`), banning `/\bMath\.random\b/`, `/\bDate\.now\b/`, `/\bperformance\.now\b/`, `/\bnew\s+Date\s*\(\s*\)/` (`:35`), excluding **only** `sidecar/index.js` (`:16,45`). So the scheduler must be cut along exactly that line — mirroring how `loop.js` takes an injected `clock` (`loop.js:84,89`) and `index.js` wires `clock:{now:()=>Date.now()}` (`index.js:276`).

**Lives in `sidecar/index.js` ONLY (the ambient half — exempt by `:16`):**
- The **now-source** — the real `() => Date.now()` (the same shape already injected at `index.js:276`).
- The **timer** — a single `setInterval` (or self-rescheduling `setTimeout`) at the tick cadence. `index.js` already owns timers (consent timeout `:178`, search throttle `:342`); the cron timer joins them. The tick body is a thin `() => applyTick(Date.now())` so the only untestable line is the timer registration itself.
- **Id minting** — `crypto.randomUUID()` for each fire's `runId` (the same call site shape as `index.js:148`); `lint-determinism` forbids bare `Math.random` outside `index.js`, so ids are minted here and injected, never inside the pure module.
- **Persistence** — the load/persist of `cron.jobs.json` (atomic temp+rename), the only `fs` in the subsystem.

> **Cadence flag:** the reference harness's 60s tick is from the `scheduler.py:5` docstring, not verified against the gateway ticker. gen picks its own cadence (60s proposed); the cadence is an `index.js` constant, not a contract.

**Becomes a PURE, lint-clean, injected-clock module `sidecar/cron.js`** (headless-testable like `loop.js`/`permissions.js`, zero ambient time). Proposed surface, mirroring `jobs.parse_schedule`/`compute_next_run`/`get_due_jobs`:

```
parseSchedule(str, now)              -> { kind:'once'|'interval'|'cron', ... }   // once needs `now` ONLY to resolve a duration→runAt; `now` is a PARAM, never Date.now()
nextFireAt(schedule, lastRunIso, now)-> int ms        // the SINGLE next fire strictly after the anchor (last run, else now)
dueJobs(jobs, now)                   -> { fire:Job[], advanced:[{jobId,nextAt}] }  // fire set + the advanced next-fire to persist (the no-backlog pair, see §3.3)
planTick(jobs, now)                  -> { fire[], skipped[{jobId,reason}], next[{jobId,nextAt}] }   // the whole tick as DATA
```

- **The `parseSchedule` four-branch shape** is the cheap win (mirror `jobs.parse_schedule:206-292`): `every Xm/Xh/Xd` → `{kind:'interval',minutes}`; bare duration `30m`/`2h` → `{kind:'once',runAt:now+Δ}`; ISO timestamp → `{kind:'once',runAt}`; 5-field cron → `{kind:'cron',expr}`. **`croniter` is a hard dependency gen cannot take** (zero-dep). The honest minimal cut: ship `interval` + `once` first (covers "every 1h"/"every 30m"/"in 2h"/timestamp — the bulk of real routines), and treat 5-field cron as a **deferred hand-rolled subset** (`*`, ranges, lists, steps) — explicitly **NOT** a port of croniter's full grammar.
- **The determinism implication is total:** because `now` is a parameter, "what fires next at 09:00" / "is this job due?" / "advance-before-run at-most-once" are all testable by feeding a fixed `now` and a fake clock; `croniter`/`ZoneInfo` would pull in ambient OS state and is the opposite of that.
- **tz/DST trap (flag in the module header):** the lint bans only the **zero-arg** `new Date()` (`:35`); `new Date(ms)` with an argument is lint-clean. If any tz math constructs a date from a passed-in `ms`, that is permitted — but a careless future "simplify to `new Date()`" regresses determinism. **For v1, server-local time (a single `clock.now()`) is the honest default** — do NOT port the reference harness's IANA `ZoneInfo` resolution, env/config cascade, or cache (`ref_time.py:37-88`). Keep the *seam* (next-fire computed against an injected `now`) so a tz layer can slot in later without touching cron-math.

> **DST scope is explicit (the silent landmine the interval-only v1 sidesteps).** v1 ships **`interval` + `once` only**, which are **duration-anchored** (the period runs from the last anchor, not a wall-clock time-of-day), so wall-clock **DST transitions do NOT affect them** — a DST gap/overlap shifts an interval job by at most the offset once, self-correcting on the next anchor. **Time-of-day / 5-field cron scheduling is deferred** (above) — and that is *exactly* where DST correctness becomes load-bearing: when that subset lands it MUST resolve fire times against a tz-aware `now` (the kept seam), and it carries its **own DST test** (spring-forward skips the missing hour; fall-back does not double-fire). So v1 has no wall-clock time-of-day scheduling and therefore no DST hole; the deferral consciously carries the tz obligation (see §6 Open Decision #1).

**Test pattern (already established twice in the suite):** inject `makeClock(T0)` from `shared/clock-rng.js` (documented `:6`, defined `:23` — `{now(),advance(ms),set(ms)}`), `clock.advance(ms)`, and assert `cron.js`'s pure functions fire exactly the expected jobs; assert `JSON.stringify(planA) === JSON.stringify(planB)` for byte-identical determinism (the exact shape `loop.replay.test.js:76` uses). Inject a fake `emit` (capture into a `seq` array), a fake `launchRun` spy, a fake `deliver` spy — the DI-purity precedent `permissions.test.js:116,122-125` sets.

### 3.2 The CronJob record + save-safe store

The persisted envelope is **`{ version: 1, jobs: [CronJob...] }`** — copying the **allowlist** idiom (`index.js:76-88`): atomic `FILE+'.'+pid+'.tmp'` → `writeFileSync` → `renameSync`; load → missing/corrupt → `{version:1,jobs:[]}` (fail-closed); persist **throws** on failure so a failed create/edit surfaces rather than silently "scheduling." Location: **`WORKSPACES/cron.jobs.json`**, a sibling of `permissions.allow.json` and the per-agent notebook — **outside** every `WORKSPACES/<aid>/` fs jail, so the agent's own `fs.*` tools can neither read nor rewrite its own schedule. (the reference harness stores `~/.ref-harness/cron/jobs.json` with the same atomic temp+rename + `{"jobs":[...]}` wrapper, `jobs.py:471-487`, but **has no `version` field** — the `{version:1}` envelope is a gen addition matching the allowlist, not a port.)

The smallest honest `CronJob` shape (re-derived from the canonical `jobs.create_job:638-671`):

```

  name:          string,
  prompt:        string,        // "" allowed

  scheduleDisplay: string,      // human label, from parseSchedule
  agentId:       string,        // which agent runs (validated /^[A-Za-z0-9_-]{1,40}$/, reusing index.js:54)
  model:         string|null,   // per-job override (gen already supports per-run model); null → boot-frozen default
  deliver:       string,        // 'local' default; 'channel:<chatId>' once messaging lands
  enabled:       boolean,

  repeat:        { times: number|null, completed: number },   // times=null = forever; one-shot auto times=1
  createdAt:     string,        // ISO, minted in index.js
  nextRunAt:     string|null,
  lastRunAt:     string|null,
  lastRunId:     string|null,
  lastStatus:    'ok'|'error'|null,
  lastError:     string|null,
  lastReason:    string|null,   // last agent.run.end reason (done|max_iters|budget|cancelled|error|refusal) — reuse the frozen enum
  // record-the-field, defer-the-consumer (the reference harness fields with NO gen runtime consumer yet — store faithfully, no migration later):
  skills:        string[],      // gen has no skill store (REF-HARNESS L8 → RPG-2); store, do not consume

```

**Dropped vs recorded (justified):**
- **Drop now:** `skill` (legacy single-skill mirror — gen has no legacy data), `provider`/`base_url` (single-provider OpenRouter; REF-HARNESS L5 defers ProviderProfile), `no_agent`/`enabled_toolsets`, `paused_at`/`paused_reason` (fold into one optional field only if a consumer needs it), `origin`/`last_delivery_error` (delivery-origin is a channels concern — add with the messaging integration), `updated_at` (replaced by the `version` envelope), and the `threading.Lock` (no Node analogue — single-threaded async; prime directive clause 2).
- **Record the field, defer the consumer:** `skills`, `script`, `workdir`, `contextFrom` — no gen runtime consumer today; store them so a later commit wires the consumer with no migration, exactly the REF-HARNESS L5/L8 rule ("land it the commit before the consumer exists").
- **The `id` path-component guard is real and worth keeping:** the id is used as a path component for any output dir; validate it is a single safe component (the fs jail already rejects `..`/absolute/drive, `fs.js:47`) before any output-path use.

**Lifecycle ops** (pure reducer over the job array — no clock, no fs, no rng; timestamps/ids injected): `create`, `update` (rejects immutable `id`; recomputes `nextRunAt` when schedule changes unless paused), `pause`/`resume` (= enable/disable; resume recomputes `nextRunAt` from now), `markRun` (writes `lastRunAt`/`lastStatus`/`lastError`/`lastReason`, increments `repeat.completed`, deletes the job on repeat-limit exhaustion), `remove`. The reducer lives in a clock-free module; the wall-clock/id/fs all live in `index.js`.

### 3.3 The scheduler tick + missed-run/catch-up + overlap/concurrency + crash recovery

**The tick is a single pass, not a loop** (mirror `scheduler.py:1970`): on each `setInterval` wake, `index.js` reads `now = Date.now()`, calls the pure `planTick(jobs, now)`, applies the returned plan (persist advances, launch fires, emit `cron.*`), and returns. The wall-clock repetition is the `setInterval`, not the math.

**Missed-run / catch-up policy — fast-forward / skip, NOT run-each-missed** (the subtlest area; mirror `jobs._get_due_jobs_locked:1032-1062`): for a recurring job whose `nextRunAt <= now`, compute a **grace window** (the reference harness: half the period, clamped 120s–7200s, `_compute_grace_seconds:341-370`). If late by **more than grace**, declare it a *stale missed run*: fast-forward `nextRunAt` to the next future occurrence and **skip** (emit `cron.skipped{reason:'caught-up'}`). Within grace, fire **once**. So a host down for hours fires **at most one** catch-up per recurring job, never a backlog burst. **For interval jobs the grace `period/2` is trivial and dependency-free**; the croniter-based grace period-measurement (`jobs.py:358-366` constructs croniter twice) is accretion deferred with the cron-expr subset. One-shots get a fixed small grace and are **permanently ineligible once `lastRunAt` is set** (`jobs.py:328-329`).

> **`cron.skipped` reasons are net-new gen signal, not a mined the reference harness enum (flag).** the reference harness emits **no** structured skip event — it only logs *lines*: `"Job %s already running — skipping"` (`scheduler.py:2111`) and `"Fast-forwarding to next run"` (`jobs.py:1046-1053`). gen re-derives the *math* of `_get_due_jobs_locked` but the `cron.skipped{reason ∈ ['already-running','disabled','caught-up','no-capability','stale-lock-reclaimed']}` rung is a fresh structured signal gen adds (§3.8), not an enum ported from the reference harness. "Mirror `jobs._get_due_jobs_locked`" means *re-derive the fast-forward/skip decision*, not *port an enum that doesn't exist*.

> **The no-backlog guarantee is a PAIR (flag).** `nextFireAt` advances by a *single* period from the anchor; the fast-forward to "next future" happens in `dueJobs`, not in `nextFireAt`. If you re-derive `nextFireAt` alone without the `dueJobs` fast-forward, you lose the no-backlog guarantee — they must ship together (`jobs.py:389` vs `:1044`).

**Overlap / concurrency — one-run-per-job (SKIP, at-most-once-in-flight) with a SELF-HEALING lease:** the reference harness keeps a process-global `_running_job_ids` set + `_submit_with_guard` refuses to dispatch a job already running (`scheduler.py:166-167,2110-2112`), and even its `finally` (`scheduler.py:2119-2121`) does **not** cover a hung worker. gen's analogue must be a *self-healing lock, not a bare `Set` add/clear* — a zombie run that never emits `agent.run.end` must never permanently wedge its job out of the schedule:
  - **(a) Clear on EVERY terminal path, in a `finally`.** The in-flight entry is released not only on the happy `agent.run.end`, but on `agent.run.error`, on the run's `AbortController` abort, AND on any uncaught throw in the reply-assembler — never only on "completion."
  - **(b) A lock LEASE, keyed by start time.** Store a **`Map<jobId, startedAtMs>`** (not a `Set`) in `index.js`. At the top of each tick, evict any entry older than a max-run ceiling (a new `CRON_MAX_RUN_MS`, default the `maxIters × toolTimeoutMs` ≈ 8-min worst-case bound from above) **and `abort()` that run's `AbortController`**, emitting `cron.skipped{reason:'stale-lock-reclaimed'}` (the new enum value added to the `cron.skipped` rung in §3.8). This guarantees a hung/zombie run is reclaimed within one lease window: the next tick aborts it and the job becomes eligible again.

A normal in-flight job is checked before dispatch (emit `cron.skipped{reason:'already-running'}` if locked). Combined with **advance-before-run** (the advanced `nextRunAt` persisted *before* launch), a long job that overruns its next tick is simply not re-dispatched; the next tick after it completes (or after the lease reclaims it) finds it due naturally. **Across different jobs:** gen dispatches serially in-process through the one `runOnce` host — the Python parallel/sequential pool split and `TERMINAL_CWD` env mutation are accretion (`scheduler.py:2095-2154`), left in the mine. The cross-process `.tick.lock` (fcntl/msvcrt, `scheduler.py:231-235`) is unnecessary — gen is a single in-process host with no second ticker process.

**Crash recovery — TWO halves, both required.** The plan must cover both *don't double-fire* AND *do resume what was missed while down*:

1. **At-most-once across restart (don't double-fire):** persist the advanced `nextRunAt` **before** launching the run (the advance is a returned value from the pure plan, applied by the host). If the process crashes mid-run, the bumped `nextRunAt` means the job won't re-fire on restart; `markRun` later overwrites `nextRunAt` from `lastRunAt` on completion (`jobs.py:902,939-965`).

2. **BOOT / RESUME reconcile (actually resume after restart):** at startup, when the env gate is on, `index.js` **loads `cron.jobs.json` and runs ONE immediate `applyTick(Date.now())` BEFORE registering the `setInterval`.** This is what makes a restart *resume* jobs rather than merely not-double-fire: the pure dueJobs fast-forward/catch-up math (§3.3 missed-run policy) is applied to runs that elapsed while the host was down, so a recurring job whose `nextRunAt` passed during downtime gets **exactly one** catch-up fire within grace (else fast-forward+skip) — never a backlog. State it plainly: *a restart re-arms the timer **and** runs an initial reconcile tick; the catch-up policy of §3.3 (fire one within grace, else fast-forward+skip) is what makes resume safe.* Without this step the "resume jobs after restart" goal is unmet — the timer would only arm for *future* fires and silently drop everything missed during downtime.

A Commit-4 test asserts both: (1) at-most-once — call pure `planTick`, persist, "restart" with the same fake clock, assert no double-fire; (2) resume — persist a recurring job with `nextRunAt` in the past, simulate restart with a fake clock advanced past one grace window, assert **exactly one** catch-up fire (not a backlog) and that the timer is then armed.

**A throwing job does NOT kill the scheduler:** wrap each fired run in a try/catch that records `lastStatus:'error'`+`lastError` and continues the dispatch loop — pure bookkeeping on the job record (the existing `agent.run.error{transient}` rung + the L3 classifier handle the run-level error vocabulary; no ref-style three-layer nesting). The "never silently disable a recurring job" invariant is worth keeping: a recurring job that can't compute a next run goes `state:'error'` but stays `enabled` (`jobs.py:910-929`); only one-shots flip to `enabled:false, state:'completed'`.

**What actually bounds a hung/idle run (the hang-guard — name it explicitly):** `maxIters:16` + `maxCostUsd:1.00` (`index.js:31`) alone do **NOT** bound a run that hangs with no token activity — neither cap advances while a tool never returns, and `loop.js` has no wall-clock/idle deadline (only `signal.aborted` at `:129,145,162`). The real bound is **`CAPS.toolTimeoutMs:30000`** (the per-tool timeout enforced at `sidecar/tools/registry.js:33`): every tool call either returns or times out in ≤30s, so the worst-case run duration is `maxIters × toolTimeoutMs` ≈ **8 min**. Without naming `toolTimeoutMs` as the guard, "per-run caps cover the runaway/hang case" is incomplete: a tool that never returns would otherwise hold the in-flight lock forever and wedge that job (see the §3.3 self-healing lock below). gen has **no** run-level wall-clock/idle kill of the reference harness's kind — that is a deliberate gap raised in §6 Open Decision #10. **Left in the mine:** the inactivity-timeout poller + activity tracker + `agent.interrupt` (`scheduler.py:1759-1845`, default `REF-HARNESS_CRON_TIMEOUT` 600s), the prompt-injection scanner, MCP-orphan reaping, credential-pool/provider-fallback wiring.

**Transient-failure retry/backoff (the failure path beyond isolation).** Isolation (above) keeps one error from killing the scheduler, but it is *not* the whole failure story: a run that ends `reason:'error'` with **`transient:true`** (network/429/5xx — the honest signal the L3 classifier already emits at `loop.js:157`, currently unused by any cron consumer) deserves a bounded retry, not a full-period wait. **Policy:** on a fired run ending `transient:true`, set `nextRunAt = now + smallBackoff` (e.g. 60–120s, not a full period), store `retryCount` on the `CronJob`, cap at **N attempts per scheduled occurrence**, and reset `retryCount` on the next clean fire. A **permanent** error (`transient:false`) records `lastError` and waits the normal period — no retry storm. This is a small pure addition to the `markRun` reducer (it already owns `lastStatus`/`lastError`); the backoff time is computed in `index.js` from the injected `now`. **If retry is out of scope for v1, it is deferred-with-a-note:** see §6 Open Decision #11 — it must not be silently absent.

### 3.4 The fire → runOnce bridge (in-process emit sink, surface:'autonomous', trigger:'schedule')

A fired cron job is a clean `runOnce` caller. The bridge is **in-process, not a `/api/run` HTTP loopback** — matching the reference harness's own in-process `agent.run_conversation` (`scheduler.py:1786`) and the messaging decision (`MESSAGING_INTEGRATION_PLAN.md:106-109`). A loopback would re-serialize the body and lose the in-process `emit`.

**The in-process emit sink** (structurally identical to the messaging hub `§3.3`): `index.js` builds an `emit` still wrapped by `makeEmitter` (so scheduled runs get the same frozen-event validation + redaction the browser gets) over an in-process `bus.emit`, not `res.write`. The sink: on `agent.run.start` capture `runId` (`loop.js:125`); on `agent.token` `buf[runId] += payload.delta` (the canonical reassembly `harness.js:91`; there is **no** `agent.message`/`agent.reply` event — `agent.token` is the only honest reply path); on `agent.run.error` `errMsg = payload.message`; on `capdenied` `errMsg = 'no '+need+' — '+reason`; on `agent.run.end` the turn is over — the buffered text is the result, `reason` says whether it completed (`done`) or truncated (`max_iters`/`budget`/`cancelled`).

**The exact runSpec a fire builds** (the fields `index.js:138` destructures, sourced for a no-browser caller):
- `key` — **boot-frozen `process.env.SKYNET_OPENROUTER_KEY`** (net-new, beside `index.js:73`; shared with messaging §3.5). Threaded into `runOnce`'s provider+web-tools exactly as the browser's `key` (`index.js:187,216`).
- `model` — the stored job's `model`, falling back to **boot-frozen `process.env.SKYNET_DEFAULT_MODEL`**.
- `system` — the job's persona (a fixed config persona, optionally per-agent).
- `messages` — the job's `prompt` as the user turn (cron is a fresh task per fire; no live transcript — the reference harness also clears session vars, `scheduler.py:1524-1528`).
- `agentId` — the job's `agentId` (e.g. `cron_<jobId>` namespace so its notebook/workspace/allowlist don't collide), validated `/^[A-Za-z0-9_-]{1,40}$/`.
- `isTask: true` — a scheduled run is a task; the `supportsTools` pre-check (`index.js:221`) still applies.
- **`surface: 'autonomous'`** and **`trigger: 'schedule'`** — the two params `runOnce` must accept (today both hardcoded: `surface:'interactive'`@`index.js:211`, `trigger:'directive'`@`:222,277`).

The capability projection is **identical** to a directive run — no special-casing: `index.js:195-201` builds the station and calls `resolveTools(agentId, station)` (a pure projection that reads no clock/env/trigger, `resolve.js:21-46`); object placement = the run's authority ceiling, scheduled or not. A cron agent whose room has no `cabinet` cannot touch files — same rule, same code path; removal-revokes-next-turn holds for cron because tools re-resolve per run.

> **B1/B2 (signature corrections, flagged):** the extracted `runOnce` body also closes over `runId` (created at `index.js:148`) and the consent `prompt` channel (`promptConsent`, `:163-181`). The clean fix: add `runId` and an optional `prompt` to the signature. > **The safety property depends entirely on Commit 4a.** The whole unattended-consent guarantee of §3.5 holds *only if the cron caller actually passes `surface:'autonomous'`* — which in turn requires Commit 4a to have added the `surface` param to `runOnce`. If 4a is skipped or deferred, a cron fire inherits the hardcoded `surface:'interactive'` (`index.js:211`) + `promptConsent`, and every ungranted mutation stalls to the 120s auto-deny instead of denying synchronously. ### 3.5 UNATTENDED CONSENT (default-deny + pre-blessed allowlist + hardline floor) — the safety keystone

A cron run has **no human at the keyboard**. The broker already has the exact rung for this; the entire story is **pass `surface:'autonomous'`**. The ladder walked for a scheduled run (`permissions.js:81-99`):

1. **HARDLINE (tier 1, `:84-85`)** — `hardlineFloor` (`index.js:102-107`) runs **first**, before any flag. A write to `.env`/`.git` is denied with the anti-retry suffix regardless of bypass. The floor stands for cron exactly as for directive runs — the gen analogue of the reference harness's unconditional `HARDLINE_PATTERNS` floor (`approval.py:260-282,1116-1124`).
2. **BYPASS (tier 2, `:86-87`)** — only if frozen `FULL_ACCESS` (`index.js:73`, the gen analogue of the reference harness's `_YOLO_MODE_FROZEN` frozen at import to defeat prompt-injection escalation). If the operator set machine-wide `SKYNET_FULL_ACCESS`, cron inherits it — the operator's explicit, boot-frozen decision; still below the hardline floor.
3. **CACHE (tier 3, `:88-89`, via `granted()` `:74-79`)** — **the pre-bless channel for cron.** `grantsPermanent = loadAllowlist()` from `WORKSPACES/permissions.allow.json` (`index.js:76-88`), a Set of `capability:scope` danger keys. To let a scheduled job write files unattended, the user pre-blesses e.g. `fs.write:write` / `notebook.write:write` **once, interactively, in a normal directive run** (the `always` decision persists it). Every future cron run reads it back here and auto-allows that class — no human needed. The allowlist lives **beside** the fs jail (sibling), so the agent's own `fs.*` tools can neither read nor self-edit it — the gen analogue of why the reference harness freezes YOLO and gates writes to `~/.ref-harness/config.yaml`.
4. **RESOLVE (tier 4, `:90-98`)** — `surface` decides:
   - read-only, non-network → **auto-allow** (`:91`): a cron job that only reads files / queries the notebook needs no human and no pre-bless.
   - **`surface === 'autonomous'` → DEFAULT-DENY** (`:92`): `return { allow:false, reason: SILENCE }` synchronously, `SILENCE = 'autonomous run cannot self-approve this action — silence is not consent'` (`:41`). `consent.grant` is **never** called automatically (`:101-102`). The interactive `prompt` branch (`:96`) is **unreachable** for cron (`surface !== 'interactive'`), so the run never await-pauses on a prompt no one answers.

**Net behaviour for an unattended run:** read-only/non-network → silently works; pre-blessed danger class → silently works; everything else mutating → default-denied with `SILENCE`, producing the paired isError 'denied' result (`sidecar/tools/registry.js:79`) so the run continues honestly and finishes/reports rather than hanging.

This is **strictly more principled than the reference harness's posture.** the reference harness's cron default-deny is *narrower than it sounds*: it applies **only to the dangerous-pattern subset of shell commands** (`detect_dangerous_command`). A command that is **not** matched as dangerous is **auto-approved in cron context regardless of `cron_mode`** — the non-interactive non-gateway fall-through returns `{"approved":True}` at `approval.py:1131-1133` (non-dangerous) and `:1156-1161` (even dangerous, when not `REF-HARNESS_CRON_SESSION`+`cron_mode:deny`), with a logged warning (mirror at `:1379-1396`). So the reference harness cron is *pattern-based default-deny on the dangerous subset of shell commands* via `approvals.cron_mode: deny` (`approval.py:1143-1153`), and the single config key `cron_mode: approve` removes even that, flipping the dangerous subset to **auto-approve everything-not-hardline**. gen's posture is **capability-scope-based** and default-deny **by construction** (`surface:'autonomous'`) across *every* ungranted mutating capability — not a pattern list — with **no global "approve everything" switch**, only per-danger-class pre-blessing. One-line verdict: gen avoids the reference harness's "flip one config key to auto-approve everything" opt-out by making consent a per-danger-class capability grant rather than a pattern-list bypass that only ever covered the dangerous-command subset in the first place.

### 3.6 DELIVERY (reuse the channels seam + local deliverable file + in-app notification; the [SILENT] no-spam check)

A fire completes with no browser attached. Three honest sinks, **additive** — a fire may write a file, queue an in-app cue, and (if configured) push to a channel:

- **(a) Messaging CHANNEL — reuse `adapter.send`, do not rebuild.** the reference harness resolves `deliver` against a `_HOME_TARGET_ENV_VARS`/`_KNOWN_DELIVERY_PLATFORMS` matrix with a live/standalone dual-send (`scheduler.py:659-851`, `116-142`). gen's analogue is the messaging plan's seam: `adapter.send(chatId,text)` (the structural match to the reference harness's `runtime_adapter.send(chat_id,text,metadata)`) + the hub's chunk-to-`MAX_MESSAGE_LENGTH` + the **`channel.delivery{channel,chatId,runId,ok,chunks,reason}`** rung (`MESSAGING §3.1,§3.3,§3.7` — **frozen by MESSAGING Commit 3, not yet in `shared/events.js`**; an implementer must not expect to find a `channel.*` rung in the file today). A cron delivery is the identical "final assistant text → chunk → `adapter.send`" path; the only difference is the trigger (`schedule`) and the target (a configured channel record vs an inbound chat). **Dependency:** sink (a) requires the messaging adapter/hub to exist (MESSAGING commits 1-5, unbuilt). Until then, (b)+(c) are the available sinks. **Do NOT port** `Platform` enum / dual-send / `PlatformRegistry`.
- **(b) Local DELIVERABLE FILE — already works end-to-end, zero new write code.** The agent's `fs.write`/`fs.append`/`notebook.write` tools already emit the validated `deliverable` event from the producer (`fs.js:29`, `notebook.js:38`), landing the file in the jailed `WORKSPACES/<agentId>/`, viewable via the read-only `GET /api/file?agent=<id>&path=<rel>` route (`index.js:355-378`). the reference harness's `deliver:'local'` = "persist a file, emit nothing" (`scheduler.py:432-433,676`); gen's local sink reuses the existing tools + `/api/file` verbatim — the ROUTINES panel renders the link from the last-result record.
- **(c) In-app NOTIFICATION — reuse the persisted `notify` rung.** `StationUI.notify` pushes `{id,t,txt,cls,read:false}` to `store.notifs` (`stationui.js:440-445`) and bumps the unread badge via `badges()` (`:459-463`). **Honest catch:** `store.notifs` is browser-side; the sidecar can't write it while the app is closed. The honest pattern: the sidecar records the result server-side (the `cron.result` rung + the job's `lastStatus`/`lastReason`/`lastError`), and on next app open the ROUTINES panel reconciles **unseen results — successful AND failed — into `notify()`** (the badge appears next open because the *server* has the result, not because we faked a notification). **The reconcile is symmetric:** an errored run or a failed delivery surfaces as a **red/`warn` notify cue + the `lastError` text in the row**, not only successes as a green cue — the §3.9 honesty mandate ("never a green last-run ok without a real result") must equally guarantee a *visible failure when one occurred*, so an unattended job that errored or whose alert failed to deliver is flagged when the user returns rather than buried in a log line.

**Delivery-FAILURE behaviour (not just the failure signal) — output is never lost.** §3.8 defines `cron.result{outcome:'failed'}` as the failure *signal*; this is the failure *behaviour*:
- **(a) Persist BEFORE send.** The run OUTPUT is always recorded server-side — the job's last-run record (the reply text + `lastRunId`/`lastReason`) and the local deliverable — **before** any channel send is attempted, so a failed send never loses the work (mirror the reference harness saving output at `scheduler.py:2052` before the delivery decision). Delivery is a step *after* the result is safe, never a precondition for keeping it.
- **(b) On `adapter.send {ok:false}`** (after the one bounded resend the messaging plan allows, `MESSAGING:98`): emit `cron.result{outcome:'failed', reason}` **AND** record `lastStatus:'error'`/`lastError` on the job, so the ROUTINES panel surfaces the failed delivery on next open (§3.6c symmetric reconcile) — not just a transient log line.
- **(c) Local-sink failure path.** If the deliverable `fs.write` is **consent-denied** under `surface:'autonomous'` (the §3.5 default-deny), the run **still records the reply text in the last-run record**, so the result is recoverable via `GET /api/file` or the panel row — never silently dropped. A denied write degrades the *sink*, not the *result*.

**The [SILENT] no-spam check — a pure post-run check on the final assistant text.** the reference harness prefixes every cron prompt with a hint ("if there is genuinely nothing new to report, respond with exactly `[SILENT]`", `scheduler.py:1133-1144`) and does a post-run check in `_process_job` (`:2064-2066`): if the final text contains `SILENT_MARKER`, **skip delivery but keep the saved audit doc** (the output is saved at `:2052` before the check). gen's equivalent: the producer half is one sentence in the job's `system` prompt; the consumer half is **one line at the `agent.run.end` reassembly point**, on the buffered text. It is pure (operates on a string already in hand — no clock, no I/O — passes `lint-determinism`). On SILENT: skip `adapter.send`/skip the `channel.delivery` emit (or emit `ok:true,chunks:0,reason:'silent'`), still persist the run output. **Deliberate divergence (flag):** use **strict-equals after trim** (`reply.trim() === '[SILENT]'`), **NOT** the reference harness's `contains` substring check (`scheduler.py:2064`) — a contains-check lets `[SILENT]` embedded in a real report accidentally suppress it. **Failed jobs always deliver** (the reference harness `:2059` — a broken alerting job is never silent); SILENT applies only on success. Skip the reference harness's *second* layer (the `delivery.py` silence-narration regex for multi-bot mirror loops) — gen has no such loops; record it as a future extension point.

### 3.7 Secrets / config frozen at boot

The two new secrets a cron run needs, **frozen at boot in `index.js`** (the only ambient-I/O module), mirroring `FULL_ACCESS`/`SKYNET_FULL_ACCESS` (`index.js:73`) and shared verbatim with `MESSAGING §3.5`:

| Secret | Source | Residence |
|---|---|---|
| OpenRouter **key** | `process.env.SKYNET_OPENROUTER_KEY` (frozen `const` at boot) | Threaded into `runOnce`'s provider+web-tools exactly as the browser's `key` (`index.js:187,216`). **Never** placed on a bus event; never embedded in a persisted `CronJob` (`redact()` exists precisely to keep keys off disk/wire, `index.js:156`). |

If neither is configured at boot, the cron subsystem **stays off** (no `setInterval`), and the existing browser path is entirely unaffected — cron is opt-in via env. A persisted `CronJob` must **never** embed the API key; the schedule fires, the key comes from the boot-frozen source.

> **No-jobs invariant (distinct from no-secrets).** Even when the env gate is **on**, if `cron.jobs.json` is empty or absent the feature is effectively off: the tick is a **pure no-op over an empty array** — it mints **no `runId`**, calls `runOnce` **zero times**, and emits at most a `cron.tick{due:0}` (or, to honor the invariant strictly, emits nothing and arms the timer lazily on first job create). An empty store changes **no** browser-path behaviour and incurs **no** run cost. So the feature stays entirely off / browser path untouched in *both* conditions: no secrets **and** no jobs.

> **Cumulative/daily SPEND-CAP gap (flag, do not necessarily build now).** Every cost ceiling today is per-run: `CAPS.maxCostUsd:1.00` (`index.js:31,275`), guarded at `loop.js:131`; `spentUsd` is loop-local and resets each run. There is **no** process-wide/per-day accumulator anywhere in `sidecar/` (confirmed by absence). For directive runs this is acceptable — a human watches. **Cron removes the human**, so the gap graduates to a genuine unattended-runaway hole: an hourly job at the default cap is up to **$24/day**; a misconfigured `* * * * *` job is up to **$1,440/day** — every individual run obeyed its cap. the reference harness cron has the *same* gap (no USD cap at all, `scheduler.py`; it even markets "Unlimited" runs/day). The eventual fix is its own ≥1-commit step **after** the basic schedule store + autonomous broker: a daily spend ledger `WORKSPACES/cron.spend.json` (`{version:1,day:'YYYY-MM-DD',usd}`, atomic persist) and a pure injected-clock "is the day rolled over / is the cap blown?" function with a gating test (the wall-clock read stays in `index.js`). **Reuse the already-frozen rung, don't invent one:** `shared/events.js:64` already defines `budget.threshold{scope ∈ ['run','day','global'], usd, cap}` — the daily spend-cap step emits `budget.threshold{scope:'day',usd,cap}` for the threshold/exhaustion signal rather than adding a new `agent.budget.exhausted` rung (that would be a redundant frozen event; "every cross-boundary signal gets a rung, prefer the existing one"). Do **not** fold it into the first cron commit.

### 3.8 New `shared/events.js` cron.* rungs (added BEFORE producers)

The cron lifecycle is genuinely new cross-boundary signal; `emitter.js` drops any unregistered name (`:17,20-23`) and `lint-emits.js` flags the literal `emit` (`:37,45`). The *run trigger itself needs none* — `agent.run.start.trigger:'schedule'` is already frozen (`events.js:24-26`). We add **five** rungs *first* (additive, no re-freeze of the run/reply path), payloads kept to the primitives `schema.js` supports (`type`/`enum`/`properties`+`required`/`items`):

```js
// ---- cron / scheduler (cross-boundary; deterministic times come from the injected clock) ----
'cron.tick':    obj(['at','due'], { at: int, due: int }),
'cron.fire':    obj(['jobId','runId','at'], { jobId: str, runId: str, at: int, scheduledFor: int }),
'cron.skipped': obj(['jobId','at','reason'],
                  { jobId: str, at: int, reason: { enum: ['already-running','disabled','caught-up','no-capability','stale-lock-reclaimed'] } }),
'cron.next':    obj(['jobId','nextAt'], { jobId: str, nextAt: int, prevAt: int }),
'cron.result':  obj(['jobId','runId','outcome'],
                  { jobId: str, runId: str, outcome: { enum: ['delivered','failed','no-op'] }, reason: str }),
```

- `cron.fire` carries `runId` so the existing run stream (`agent.run.start`/`.end`, `agent.cost`) correlates to the job **without** a new field on those frozen events. The fire is the *bridge* event; the run itself stays on the unchanged `trigger:'schedule'` contract.
- `cron.result` is distinct from `agent.run.end`: `run.end` reports the loop outcome; `cron.result` reports the *job-level* outcome including the delivery step (`no-op` = `[SILENT]`/local-only; `delivered`/`failed` = channel result). Its `reason` reuses the frozen `agent.run.end` vocabulary so the HUD's last-result labels match the `endReason` labels at `chat.js:187-190` (`'reached the step limit — say "continue"…'` / budget / cancelled). (The reply itself is reassembled from `agent.token` deltas at `harness.js:91` `full += payload.delta`, cited correctly in §3.4 — `chat.js:163-168` are the stream callbacks, not the reassembly point.)
- `at`/`nextAt`/`scheduledFor` are `int` ms epoch from the injected clock — never `Date.now()` inside backend logic.

Each rung lands with **valid + invalid `contract.test.js` fixtures** in the same commit, *before* its first producer — the discipline `REF_HARNESS_INTEGRATION_PLAN.md:284` and the `MESSAGING_INTEGRATION_PLAN.md:176-188` precedent both mandate. ### 3.9 The frontend ROUTINES panel + endpoints + whether a routine owns a workstream

1. `GET /api/cron` — list (include disabled; let the UI filter) → `{ jobs:[{id,name,schedule,scheduleDisplay,enabled,nextRunAt,lastRun:{t,reason,ok,error,runId,cost,deliverables:[{title,kind}]},workstreamId}] }`. `reason` reuses the frozen `events.js:46` enum.

3. `PATCH /api/cron/:id` — update + pause/resume via an `enabled`/`state` field (folds edit+pause+resume).
4. `DELETE /api/cron/:id` — remove → `{ok}`.

**Should a routine own a workstream? — YES: a Routine OWNS a workstream (one stream per routine), filing each fire's run/cost/deliverables via `appendRun`/`addCost`/`recordDeliverable`.** A Workstream is "one named conversation that OWNS its backend runs + deliverables + per-conversation cost" (`workstreams.js:1-5`) — exactly a long-lived routine accruing many fires. The plumbing exists and is unit-tested: `appendRun(id,runId)` auto-advances `todo→active` on the first real fire (`:160-166`, the hybrid-honest lane — a routine that *has* fired *is* active); `addCost` (`:173-179`); `recordDeliverable` (`:167-171`). **Reject "a Routine BE a workstream"** — the schedule + secrets are server-owned and must never serialize into the browser localStorage `Workstreams` slice (`serialize():90`), which would leak a secret into a redaction-free store.

> **Load-bearing caveat (flag) — corrected.** The browser-side Workstreams wiring **does** exist and is live: `chat.js:163` calls `Workstreams.appendRun(ws.id, id)` on `onRunId`, `:172` `Workstreams.recordDeliverable(ws.id, …)` on `onDeliverable`, and `:205` `Workstreams.addCost(ws.id, …)` in the run's `finally` — real calls inside the run/deliverable/cost handlers, not migration refs (`index.html:138` loads the module; `save.js:16-19` wires migration). So the §3.9 conclusion ("a Routine OWNS a workstream") is **better** supported than a "dormant / slice-2 unwired" reading would suggest. The honest remaining gap is **narrower and different:** that wiring is **browser-side** — `chat.js` drives `appendRun`/`addCost`/`recordDeliverable` off the **NDJSON stream of an interactive run**, and the `Workstreams` store is **client-side / `localStorage`-only** (`serialize():90`). A cron fire happens with **no browser and no stream**, so the server *cannot* call these browser-only methods. The real reason a routine needs a **server-side per-job stream record** (id + runIds + cost + deliverables, reconciled into the browser `Workstreams` model on next app open) is therefore "the Workstreams store is client-side and a headless fire never reaches it," **not** "slice-2 hasn't landed." The working-now option stands on that correct basis.

## 6. Open design decisions that need the user's call

1. **Schedule input format (carries the tz/DST obligation).** Ship `interval` + `once` (`every 30m` / `in 2h` / ISO timestamp) for v1 and defer 5-field cron to a later hand-rolled subset (`*`, ranges, lists, steps — not a croniter port)? Or invest in the cron subset up front? Interval+once covers the bulk of real routines, is zero-dep today, and is **duration-anchored so DST never bites it** (§3.1). The deferral consciously carries the tz/DST obligation: the deferred time-of-day/cron-expr subset MUST resolve against a tz-aware `now` and ship its own spring-forward/fall-back test (§3.1). Confirm interval+once for v1.

2. **Missed-run / catch-up policy.** Confirm fast-forward-and-fire-one-catch-up-within-grace (the reference harness no-backlog default, §3.3) vs run-each-missed (a backlog burst on restart) vs skip-all-missed (never catch up). Fast-forward-one is proposed and is the safe default for an unattended host.

3. **Overlap policy.** A job still running when its next tick arrives: **skip** (at-most-once-in-flight, the reference harness default, §3.3) vs **queue** (run after the current finishes) vs **abort-and-restart** (the messaging abort-on-new semantics). Skip is proposed (a routine is not a chat).

4. **Delivery default.** `local` (write a deliverable file + in-app cue, §3.6b/c — works with no messaging layer) vs `channel` (push off-machine, requires the messaging hub) as the per-job default. Local is proposed; channel is opt-in once messaging lands.

5. **Consent default for autonomous runs.** `surface:'autonomous'` (default-deny ungranted mutation; pre-bless danger classes in `permissions.allow.json`, §3.5) is the only honest floor with no browser. Confirm there is **no** "cron approve mode" switch (the reference harness opt-out gen deliberately omits) — autonomous-default-deny is the proposed posture.

6. **Daily spend cap (§3.7 gap).** Build the cumulative `cron.spend.json` ledger now (an extra ≥1-commit step after Commit 4b), reusing the **already-frozen** `budget.threshold{scope:'day',usd,cap}` rung (`events.js:64`) for the exhaustion signal — or ship per-run caps only and accept the N×$cap unattended exposure for v1? A daily cap is strongly recommended *before* exposing minute/hour-granularity schedules.

7. **Whether a routine owns a workstream.** Routine-owns-a-workstream (one stream per routine, §3.9 — needs slice-2 wiring or a server-side per-job stream record) vs routine runs spill into General (collision-prone) vs no workstream link for v1. Routine-owns-a-stream is proposed; the working-now path is the server-side per-job record.

8. **Blueprint catalog scope.** The ~5 domain-agnostic seeds (briefing / station-recap / `[SILENT]`-monitor / topic-digest / custom-prompt-on-a-schedule, §3.10) vs a larger catalog vs custom-prompt-only (no catalog). The 5-seed catalog is proposed; the lifestyle blueprints are dropped.

9. **Run-history retention.** Last-run snapshot only (`lastRunAt`/`lastStatus`/`lastReason` on the record, the reference harness default) vs a bounded per-job output history (separate files, the reference harness `output/{id}/{ts}.md` shape, deferred to a run-log) vs full retention. Last-run-snapshot is proposed for v1; a deeper history rides the future ledger/run-log.

10. **Run-level wall-clock / idle kill (§3.3 hang-guard).** gen has **no** run-level wall-clock or idle-token deadline — the worst-case run is bounded only by `maxIters:16 × toolTimeoutMs:30000` ≈ 8 min (`index.js:31`, `sidecar/tools/registry.js:33`), and the §3.3 self-healing lease reclaims a zombie that exceeds `CRON_MAX_RUN_MS`. Is the lease ceiling enough, or do we add a per-job run-level deadline (a `CRON_MAX_RUN_MS` passed as the run's hard cap), given unattended is exactly where the reference harness felt the need (`REF-HARNESS_CRON_TIMEOUT` default 600s, `scheduler.py:1767-1845`)? The lease is proposed as the minimum; an explicit per-run deadline is the stronger option.

11. **Transient-failure retry/backoff (§3.3).** On a fired run ending `agent.run.error{transient:true}` (the honest L3 signal at `loop.js:157`, currently unused by cron): schedule **one bounded retry** at `now + 60–120s` (capped at N attempts per occurrence, `retryCount` on the job, reset on the next clean fire) — or ship v1 with isolation only (a transient failure just waits the full period) and defer retry? Bounded-retry is recommended for unattended jobs (a 429 at 03:00 shouldn't lose the whole occurrence); if deferred it is a §3.3 deferred-with-a-note, not silently absent.
